# Part 0. 報告：君の環境を見て、計画を2か所直した

**質問ではないので、読むだけでいい。** ただし「そうじゃない」という点があれば言ってほしい。

## ① 合成データのレンダリングは **EEVEE** を既定にした

送ってくれた情報の Cycles の欄に、計算デバイスとして **CPU しか挙がっていなかった**（`CPU device capabilities: AVX2` の1行だけ）。GPU が Iris Xe（CPU内蔵のGPU）なので、そもそも Cycles の GPU レンダリングが使えない構成だと思われる。

Cycles を CPU で回すと、**20方向 × 何セットも** レンダリングする本プロジェクトでは時間が溶ける。

**だから合成データの生成は EEVEE を既定にする。**

これは手抜きではなくて、**要件から見て EEVEE で足りる**という判断。こちらが合成データに求めているのは「綺麗な絵」ではなく、

- カメラ行列・シルエット・正解形状と**辻褄が合っている**こと
- 特徴点が取れること、輪郭がはっきり出ること

の2点だけで、物理的に正確な光の回り込みは要らない。（Cycles は「レンダリング品質を上げると復元精度が変わるか」を見る追加実験で使う。余力があれば。）

**→ 関連する質問は Part 2 の N3・N4。**

## ② ボクセルを「分割して」処理する実装にした

ボクセル（3D版のピクセル）を 256×256×256 で切ると 1677万個になる。**この全部を一度に配列に展開すると、一時的に 1GB 近くメモリを食う。**

内蔵GPUはメインメモリを間借りするので、その分も差し引かれる。

**だから最初から「塊に分けて順番に処理する」書き方にする。** これは関口側（ボクセル彫刻）の実装方針なので君の作業は変わらないが、**W12 のペアプロで一緒に触る箇所なので先に共有しておく。**

**→ ただし、そもそも何ボクセルでいけるかはメモリ次第。Part 1 の Q-b で聞いている。**

## Q-c. このプロジェクトにリアルタイム描画は登場しない。了承できるか？

第1版 Q2 と同じ質問。**送ってもらったアドオン構成を見て、確認の必要性がむしろ上がった**（後述 Part 2 の N8）。

**正直に言う**：このプロジェクトは静止画の一括処理で、**リアルタイム描画は本質的に出てこない。** Unity も、数値計算部分との言語をまたぐ接続コストが高いため不採用にしてある。

だから君の旨味は、リアルタイム描画ではなく**ジオメトリ処理とレンダリング**に置くことになる。3DCG研究の評価軸としてはジオメトリ処理のほうがむしろ王道ではあるが、**君がやりたいことと違うなら意味がない。**

受け皿として、ボクセルが削られていく過程をリアルタイム表示するビューアは用意してある（デモとして一番見栄えがする）。ただし優先度は最後。しかも内蔵GPUなので、解像度は落とす前提になる。

**【これが変わる】** 「どうしてもリアルタイム描画を主軸にしたい」なら、**テーマ自体を再検討したほうがいい。** 第二候補として「物理シミュレーション × Unity」を残してある。**着工前なら乗り換えコストはゼロ。着工後だと全部無駄になる。**

```
回答:
☑ 了承する。ジオメトリ処理で問題ない
□ 了承するが、ビューアは優先度を上げたい
□ リアルタイム描画を主軸にしたい（テーマ再検討）

コメント:「数値計算部分との言語をまたぐ接続コストが高いため不採用にしてある。」との記述があるが、実装で処理がPythonだと遅いなどの問題がある場合はc++など他言語を用いた開発でも可能(プログラミング知識や技術については最低限あるが、本開発においては生成AIを用いたコーディングを控えたいため、実装に時間がかかると考えられる)
```

## Q-e. 「主担当＋副担当」という進め方でいいか？【2026-08-15 修正】

第1版 Q3 と同じ質問だが、**中身を1か所直した。**

**直した理由**: 第1版では副担当を「レビューするだけ。実装はしない」と書いていた。**これは書き方を間違えた。** 実際にやりたいのはそういうことではなく、

> **詳しいほうが主軸になって、一緒に作る。**

**副担当も手を動かす。** ただし全部を2人で書くと開発速度が半分になって確実に間に合わない（工数計算済み）ので、**「どこを一緒に書くか」を先に決めておく**という形にした。

### 修正後の役割

| 役割 | やること |
|---|---|
| **主担当** | **設計を決める。** そのモジュールの中核（専門知識が要る部分）を実装する。**副担当がやる部分を切り出して、必要な説明をする** |
| **副担当** | **切り出された部分を実装する。** そのうえでPR全体をレビューし、「何をやっているか説明できる」ところまで理解する |

つまり違いは「**書くか読むか**」ではなく「**設計を決めるか、決まった設計の中で書くか**」。

### 「副担当がやる部分」の選び方

適当に切ると雑用の押し付けになるので、原則を1つ置いた。

> **副担当が実装するのは、「副担当自身の専門が顔を出す部分」を選ぶ。**

君が関口のモジュールで実装する部分は、例えばこういうもの（計画書 §3-6 に全部書いてある）。

| 関口のモジュール | **君が実装する部分** |
|---|---|
| カメラ姿勢推定（DLT） | **推定したカメラで3D点を画像に投影し直して、元の点と重ねて描く可視化** |
| バンドル調整 | **ヤコビアン（巨大な疎行列）の形を絵にする**、収束していく様子のアニメーション |
| CG法ソルバ | **残差が減っていくグラフ**、前処理あり/なしの比較図 |
| 凹み部分の補正 | **ボクセルと点群を重ねた3D可視化**（どこが削られたか） |

**これは雑用ではない。** 関口のモジュールは「数字は出るが目に見えない」ものばかりで、**絵が付かないとデバッグも成果発表もできない。** かつ、この部分は君の専門が最短で効く。逆に関口は、君のモジュールでは**メッシュ簡略化の誤差行列**や**テクスチャの可視性判定**みたいな線形代数・幾何が出る部分を実装する。

### 前提：**普段から一緒の場所で作業するつもりでいる**

誤解のないように書いておくと、**「分担する」＝「別々に作業する」ではない。**

平日はほぼ毎日会えるので、**普段から同じ場所で作業して、詰まったらその場で聞く**形を想定している。任せっきりにするつもりはない。

そのうえで、**「同じ場所にいるか」と「同じコードを2人で書くか」は別の話。**

| | 内容 | 開発速度への影響 |
|---|---|---|
| **同席して、各自が自分の担当を書く** | ★**これが普段の姿** | **落ちない** |
| 同じコードを2人で書く（ペアプロ） | **3か所だけ**（P1 参照） | **半分になる** |
| 各自の都合の時間に作業 | 会えない週はこれ | 落ちない |
