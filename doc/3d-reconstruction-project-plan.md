## 2. データ取得方針

### 決定：Blender合成データで着工し、Phase 0 最終週に実写を1セット通す

### 用語

- **レンダリング**: Blender内に3Dモデルを置き、仮想カメラから「写真を撮る」こと。出力は通常の画像ファイル。
- **真値メッシュ（ground truth mesh）**: 「正解の3D形状」。復元精度を測るための比較対象。
- **Hausdorff距離**: 2つの3D形状のズレの指標。「復元形状の各点から正解形状までの最大距離」。単位はmm。

### 合成データで得られるもの

Blenderに既知の3Dモデルを置き、カメラを円周上に20方向配置してレンダリングすると、以下が**全て正解付きで**手に入る。

| 出力 | 用途 |
|---|---|
| 画像 20枚 | パイプラインの入力 |
| **カメラ行列**（Blenderが知っている） | 姿勢推定（DLT・バンドル調整）の答え合わせ |
| **元の3Dモデル** | 真値メッシュ。Hausdorff距離の比較対象 |
| **シルエット画像** | セグメンテーションの答え合わせ |

### 採用理由

1. **今日から着工できる。** 回転台・背景布・照明の調達を待たない。「8月中着工」と直接噛み合う。
2. **デバッグが劇的に楽。** 誤差ゼロの完璧な入力を自作ソルバに入れて答えが合わなければ、原因は100%実装バグ。実写だと「バグなのか撮影が悪いのか」を切り分けられず、Phase 2 が泥沼化する。
3. **相方の初仕事が1週目に発生する。** 引き継ぎ資料 §5 が心配していた「相方が6週間何もできない」問題が、モック `cameras.json` を手書きするより自然な形で解決する。しかもBlenderからカメラ行列を書き出せばモックが自動生成される。

### 既知のリスクと対策

**合成画像は綺麗すぎる。** ノイズも影のムラもなく特徴点が理想的に取れるため、実写に移った瞬間に精度が落ちる。

対策として、**Phase 0 の最終週（W3）に実写を1セットだけ通す**。精度は問わず、「自分たちの被写体で特徴点が何点取れるか」という引き継ぎ資料 §7 Phase 0 本来の目的の実測値だけを取る。実写の本格導入は Phase 3（W12）から。

### 被写体の設計要件（重要）

§0 の最重要実験「①のみ / ④のみ / 統合 の3条件比較」で統合の優位を示すには、**①が失敗する条件と④が失敗する条件の両方を含む被写体**が必要である。

| 条件 | 失敗する手法 |
|---|---|
| 無地でテクスチャのない面 | ① 多視点復元（特徴点が取れず点群に穴が空く） |
| 凹んだ形状 | ④ シルエット復元（原理的に削れない） |

**マグカップはこの両方を満たす**（陶器の無地の面＋内側の凹み）。引き継ぎ資料 §6 の被写体選定は正しい。**合成データにも必ず凹み形状を含めること。** 凸形状だけのモデル（球、Suzanne等）だけで実験すると、統合の意味が数字に出ない。

推奨する合成データセット：

| データセット | 目的 |
|---|---|
| `synthetic_cup` | 主データ。凹み＋無地面を持つマグカップ相当 |
| `synthetic_bunny` | 副データ。凸形状・高テクスチャ。①単独の上限性能の確認用 |

### 3-1. 前提：工数は既に飽和している

| 項目 | 概算 |
|---|---|

| ボクセル彫刻（行列化・高速化含む） | 25h |

| I/O・CLI・テスト・CI | 30h |
| 評価実験 | 40h |
| ドキュメント | 20h |
| **合計** | **315h** |

1人あたり週8.75時間で18週。引き継ぎ資料 §1 の想定（週6〜10時間）の範囲内で成立する。

**ただしこの見積もりにデバッグ時間は含まれていない。** 数値計算のデバッグは実装の1〜2倍かかるのが普通であり、実質は450〜500h規模になりうる。超過分は §1 が許容する「余裕があれば5〜6か月」（〜2027年2月）で吸収し、それでも足りなければ §12 の撤退ラインで判定する。

**この制約から、「全てを2人で書く」という運用は採れない。** 同じコードを2人が書けば throughput は半分になる。だから「共有するかしないか」ではなく「どこを共有し、どこを共有しないか」を設計する。

### 3-2. 協働の型：「主担当＋副担当」

**全てのコードに主担当と副担当を置き、副担当はPRレビューを必ず通す。**

| 役割 | やること |
|---|---|
| 主担当 | 実装する。設計判断をする。 |
| 副担当 | PRをレビューする。**「何をやっているか説明できる」ところまで理解する。** 実装はしない。 |

**理由**

1. **速度を落とさずに知識が流れる。** 2人で書くと throughput が半分になるが、「書く1人＋読む1人」なら1.3倍程度の消費で済む。上の工数からしてこれが上限。
2. **就活で効く。**「相互レビューで互いの専門を理解した」を、PR履歴という**証拠付き**で語れる。

**規約：形式的なLGTMを構造的に禁止する**

> PRのApproveコメントには、**「このPRが何をしているか、自分の言葉で1〜3行」**を必ず書く。

これが書けないなら、まだ理解していないということ。書けるまで質問する。対面で会えるので、その場で聞けばよい。

### 3-3. 例外：2人で書く3か所（ペアプロ）

### 3-4. 相方側の技術核（新規確保）

引き継ぎ資料 §5 では相方が「作業の受け皿」になっており、3DCG研究への助走になっていなかった。以下3つを技術核として明示的に確保する。

**核1：合成データセット生成器（Blender）**

既知の3Dモデルを配置し、カメラを円周上に並べてレンダリング。画像・シルエット・カメラ行列・真値メッシュを一括出力する。CGパイプライン構築そのもの。**着工1週目から相方が主役になれる。**

**核2：メッシュ処理（Marching Cubes 以降）**

ボクセルからメッシュを起こし、簡略化・UV展開・テクスチャ投影までを担当。3DCG研究室で評価される離散幾何処理の実装経験。

**核3：離散ラプラシアン作用素の構成（共同担当）**

引き継ぎ資料 §4-4 の `(I + λL) x' = x` を、担当を割って作る。

| 担当 | 内容 | 学問的位置 |
|---|---|---|

## 4. 座標系の規約

引き継ぎ資料 §10-5 が「事故が起きやすい」と警告した箇所。**規約を決めることより、規約を破れない構造を作ることが本質。**

### 4-1. 決定：OpenCV規約に統一

| 対象 | 規約 |
|---|---|
| 世界座標系 | 右手系、**+Z が上**（ターンテーブルの回転軸）、原点は回転台の中心 |
| カメラ座標系 | **OpenCV規約**：+X 右、+Y 下、**+Z が光軸の前方** |
| 画像座標系 | **OpenCV規約**：原点は左上ピクセルの中心、+u 右、+v 下 |
| 外部パラメータの向き | **world → camera**。すなわち `X_cam = R · X_world + t` |

**OpenCV規約を選ぶ理由**：引き継ぎ資料 §8 で「OpenCVの `solvePnP` / `triangulatePoints` を回帰テストのリファレンスとして残す」と決まっている。リファレンスと規約がずれていると、答え合わせのたびに変換が挟まりデバッグが成立しない。

世界座標の「+Z 上」だけは Blender と揃える（Blenderも +Z 上の右手系）。これで**世界座標の変換は不要**になり、変換が必要なのはカメラ座標と画像座標だけになる。

### 4-2. Blender との変換

Blenderのカメラは **−Z 方向を見て、+Y が上**。OpenCVは **+Z 方向を見て、+Y が下**。Y軸とZ軸の符号が逆。

```python
C = np.diag([1.0, -1.0, -1.0])

R_cv = C @ R_blender
t_cv = C @ t_blender
```

画像の縦方向も逆（Blender/OpenGLは左下原点）：

```python
v_cv = H - 1 - v_blender
```

### 4-3. 規約を破れなくする仕組み

> **`src/recon3d/io/coords.py` の中の関数以外では、座標変換を一切書かない。**

`diag(1,-1,-1)` や `H - 1 - v` が他のファイルに現れたら規約違反。**この4行の変換が10か所にコピーされ、どこか1か所で符号を間違えて数週間溶ける**、というのが典型的な事故の形である。

機械的に検出する：

```python
# tests/test_conventions.py
def test_no_stray_coordinate_conversion():
    """io/coords.py 以外に座標変換のリテラルが現れないことを確認する。
    src/ 全体を走査し、diag(1, -1, -1) 相当のパターンを検出したら失敗。"""
```

**ペアプロ対象（§3-3）。** 2人で一度作れば、以降は互いに違反を指摘できる。

### 5-1. スキーマ

```json
{
  "schema_version": "1.0",

  "convention": {
    "world_up": "+Z",
    "handedness": "right",
    "camera": "opencv",
    "image_origin": "top_left",
    "extrinsic_form": "world_to_camera"
  },

  "image_size": { "width": 1920, "height": 1080 },

  "intrinsics": {
    "fx": 1600.0, "fy": 1600.0,
    "cx": 960.0,  "cy": 540.0,
    "distortion": {
      "model": "opencv_radtan",
      "k1": 0.0, "k2": 0.0, "p1": 0.0, "p2": 0.0, "k3": 0.0
    }
  },

  "views": [
    {
      "image": "images/img_000.png",
      "mask":  "masks/img_000.png",
      "R": [[1,0,0],[0,1,0],[0,0,1]],
      "t": [0.0, 0.0, 0.5],
      "source": "turntable_gt",
      "turntable_angle_deg": 0.0,
      "reprojection_error_px": null
    }
  ],

    "generated_at": "2026-08-20T10:00:00+09:00",
    "dataset": "synthetic_cup_20views"
  }

```

### 5-2. 設計判断の根拠

**① `convention` ブロックをファイル自身に埋め込む**

規約はドキュメントにも書くが、**データファイル自身にも書く。** 半年後に `data/` から出てきたJSONが、どの規約で書かれたか単体で分かる状態にするため。読み込み時に検証し、想定と違えば例外を投げる。

**② `extrinsic_form` を明示する**

`X_cam = R·X_world + t`（world→camera）なのか、その逆なのかを文字列で持つ。ここが曖昧だと `R` と `Rᵀ` の取り違えが起き、しかも**それらしい結果が出てしまう**ため発見が遅れる。3D復元で最も頻度の高い事故。

**③ `source` フィールドが実験設計の骨格になる**

取りうる値：`"turntable_gt"` / `"dlt"` / `"bundle_adjusted"`

引き継ぎ資料 §5 の「回転台の真値 vs ①の推定値」の切り替えが、**この1フィールドだけで表現できる。** 同じ `cameras.json` 形式のまま中身を差し替えれば、下流のコードを一切変更せずに条件を切り替えられる。§5 のモック戦略と §7 Phase 4 の比較実験が、同じ仕組みで実現される。

**④ `mask` のパスを同じファイルに入れる**

引き継ぎ資料 §5 の「④が待っているのは `cameras.json` という1ファイルだけ」を文字通り実現する。ボクセル彫刻は `cameras.json` を読めば、画像もマスクもカメラ行列も全部たどれる。

### 5-3. 読み書きと検証

`src/recon3d/io/cameras.py` に、`dataclass` ベースの読み書き＋検証を置く。**pydantic等の追加依存は入れない**（§7 の Blender 制約のため）。

検証項目：

| 項目 | 検出できる事故 |
|---|---|
| `schema_version` が既知か | 仕様変更の取り違え |
| `convention` が想定と一致するか | 規約違いのデータの混入 |
| `RᵀR ≈ I` | 回転行列の破損 |
| **`det(R) ≈ +1`** | **座標変換の符号ミス（−1なら鏡映）** |

`det(R) = −1` の検出は特に効く。座標変換の符号を間違えた場合、ほぼ確実にここに現れる。

## 7. 環境の再現

### 7-1. `uv` を採用

`uv sync` 一発で `uv.lock` から同一環境が再現される。`venv` + `requirements.txt` と違い推移的依存まで完全に固定されるため、3台（Ubuntu / Mac / Windows）の環境差を潰せる。

```bash
uv sync          # 環境構築（初回・以降とも同じコマンド）
uv run pytest    # テスト実行
```

**`uv.lock` は必ずコミットする。** これが環境同一性の根拠になる。

### 7-2. Python は 3.11 に固定【2026-08-15 確定】

**相方の実機で確認済み。Blender 5.0.1 の内蔵Pythonが 3.11.13 であるため、3.11 系に固定する。** ずれるとBlender内で自作モジュールをimportできない。

```
Blender: 5.0.1  (branch: blender-v5.0-release, hash: a3db93c5b259, 2025-12-15 Release)
Python : 3.11.13 (MSC v.1929 64 bit AMD64)
出典   : blender_system/system-info.txt（相方提出・2026-08-15）
```

当初は「Blender 4.2 LTS が 3.11 だから」を根拠に 3.11 を**仮決め**していた。実機は 5.0.1 だったが、**内蔵Pythonは同じ 3.11 系だったため、仮決めした値がそのまま確定値になった。** 計画への影響はない。

**設定**: `pyproject.toml` に `requires-python = ">=3.11,<3.12"`、`.python-version` に `3.11.13` を置き、`uv` に同じパッチバージョンを取得させる。3台（Ubuntu / Mac / Windows）で `uv sync` すれば同一環境になる。

なお Mac mini のシステムPythonは 3.13.15 だが、`uv` が 3.11 を別途取得するため問題ない。

**運用上の注意：Blender 5.0.x は LTS ではない。**

内蔵Pythonのバージョンは Blender のバージョンに紐づくため、相方が Blender を更新するとここが動く。したがって：

> **開発期間中（〜2026-12）は Blender を 5.0.x に固定する。** 更新が必要になった場合は、更新前に相談する（プロジェクトの Python 版を追随させる必要があるため）。

#### 制約1：Cycles は CPU レンダリングになる → **合成データ生成は EEVEE を既定にする**

システム情報の Cycles 欄に挙がっているのは `CPU device capabilities: AVX2` のみで、**GPU計算デバイス（Intel oneAPI 等）が列挙されていない。** つまり現状の設定では Cycles が CPU で回る。内蔵GPU である点と合わせると、20方向 × 複数データセット × 反復試行のレンダリングは現実的な時間に収まらない。

> **決定：`tools/blender_render.py` の既定レンダラを EEVEE とする。**

**根拠**: 本プロジェクトが合成データに求めるのは「**カメラ行列・シルエット・真値メッシュと整合した、一貫性のある画像**」であって、物理的に正確な大域照明ではない（§2）。特徴点検出とセグメンテーションが成立すれば要件を満たす。Cycles は、レンダリング品質の影響を見る追加実験（余力があれば）でのみ使う。

#### 制約2：マスク画像の生成では**カラーマネジメントを Standard にする**

Blender の既定のビュー変換は **AgX**（4.0 以降）で、これはトーンマッピングを掛けるため**画素値がそのまま出ない**。シルエット／マスク（`masks/*.png`）は「白=物体・黒=背景」の二値が正しく出ることが要件なので、ここでトーンマッピングが挟まると閾値処理が壊れる。

> **決定：マスク出力時は View Transform を `Standard` に設定する。** `tools/blender_render.py` の中でスクリプトから明示的に設定し、Blender の UI 設定に依存させない。

同じ理由で、**マスクはカラー画像を後から閾値処理して作るのではなく、Blender 側で直接出力する**（アルファまたは ID/クリプトマット的な経路）。手法は相方に委ねるが、**「マスクの生成方法」を `docs/notes/` に1本残すこと**（§3-7）。

#### 制約3：ボクセル 256³ はメモリ次第 → **チャンク分割前提で実装する**

256³ = 1677万ボクセル。占有グリッド自体は小さいが、**§7-5 の「行列で一括投影する」方式は中間バッファが大きい。**

| 配列 | 256³ | 128³ |
|---|---|---|
| 占有グリッド（uint8） | 17 MB | 2 MB |
| 全ボクセル中心の同次座標 `4×N`（float64） | **537 MB** | 67 MB |
| 投影結果 `3×N`（float64・カメラ1台分） | **403 MB** | 50 MB |

素直に書くと 256³ で一時的に 1 GB 前後を要求する。内蔵GPUはシステムメモリを共有するため、実効メモリはさらに目減りする。

> **決定：`geometry/carving.py` は、ボクセルをチャンクに分割して投影する実装を最初から採る。** 全ボクセルを一度に `4×N` へ展開しない。チャンクサイズはパラメータとして外に出し、環境ごとに調整できるようにする。

これはペアプロ#2（W12）の設計項目に含める。**なお §7-5 の「ループではなく行列演算で書く」方針は維持する**（チャンク内では行列演算）。E7（実装方式の速度比較）の独立変数に**チャンクサイズ**を追加してもよい。

**解像度の最終決定は W12 に実測で行う**（§16）。メモリの回答が得られ次第、事前に見通しを立てる。

#### 制約4：リアルタイムビューア（L4）の実現性は控えめに見る

表示も内蔵GPU で行われる。ボクセルが削られる過程のリアルタイム表示（§3-5 の受け皿）は、解像度を落とすか、更新頻度を落とす前提で考える。**L4 項目なので優先度は最後のまま。**

#### 好材料

- **glTF / FBX エクスポータが有効**。資料3 Q21 の「Web で見られる形式（glTF）で出力」は追加準備なしで実現できる。
- **FFmpeg 同梱**。デモ動画（回転表示・復元過程）の書き出しが Blender 内で完結する。
- **OpenVDB 12.0.0 同梱**。ボクセルデータを Blender 側で可視化・検証する逃げ道がある。自作 Marching Cubes の出力を目視で検証する用途に使える。
- **`io_mesh_uv_layout` が有効**。UV展開結果の確認（§20 相当の作業）がすぐできる。

#### 注意：**アドオン構成が示唆する相方の関心領域**

標準外の有効アドオンは VRM・MMD・Rokoko（モーションキャプチャのライブ連携）の3つで、いずれも**キャラクター／アバター／モーション寄り**の道具である。

これは既知の「相方の志向はリアルタイム・Unity・GUI寄り」（§0）と整合する。**したがって §3-5 の確認（資料3 Q2）と、志望研究室の分野の確認（資料3 Q15）の重要度が上がった。**

- 資料3 Q15 の表で「**アニメーション・物理**」に該当する場合、そこには「このプロジェクトでは直接つながらない」と明記してある。
- **着工前に Q2・Q15 の回答を得ること。** 着工後に判明すると、§3-4 で確保した技術核3つが相方にとって空振りになる。

**ただしこれは推測である。** アドオンが入っていることは、それを使い込んだことも、それを研究したいことも意味しない。判断材料として扱い、決めつけない。

## 8. ブランチ戦略とIssue運用

### 8-1. ブランチ

**`main` のみを長期ブランチとする。** `develop` は作らない（2人では過剰）。

| 項目 | 決定 |
|---|---|
| `main` | 保護。直push禁止、PR必須 |
| ブランチ名 | `feat/<module>-<topic>` / `fix/<...>` / `docs/<...>` / `exp/<...>` |
| 例 | `feat/solvers-cg`、`feat/mesh-marching-cubes`、`exp/e2-angle-condition-number` |
| マージ | **squash merge に統一**（履歴が読みやすい。public化後に読まれる前提） |
| Approve | 相手のApprove必須。**ただし W1〜W2 は必須にせず、W3から必須化**（相方がGitに慣れるまで） |

### 8-2. PRの規約

1. **PRの説明文は、相手の専門外を前提に書く。** 「何を」「なぜ」を1〜3段落。
2. **Approveコメントには「このPRが何をしているか、自分の言葉で1〜3行」を書く。** 形式的なLGTMを構造的に禁止する（§3-2）。
3. 1 PR = 1 Issue = 1トピック。複数のことを混ぜない。

### 8-3. Issue の粒度

> **1 Issue = 1 PR = 1〜2週で終わる単位。**

Phase単位のIssue（例：「Phase 2 を完了する」）は作らない。進捗が見えず、レビュー単位としても大きすぎる。

**ラベル**

| 種類 | 値 |
|---|---|
| 領域 | `area:io` `area:geometry` `area:solvers` `area:vision` `area:mesh` `area:fusion` `area:viz` `area:docs` |
| フェーズ | `phase:0` 〜 `phase:4` |
| 特殊 | `pair`（ペアプロ対象）、`blocked`、`experiment` |

**運用**

- GitHub Projects のボードを1枚：`Todo` / `In Progress` / `In Review` / `Done`
- **週1回、対面15分で次週分のIssueを2人で切る。** 会えるという条件を活かす。
- 対面で決めたことは、その場でIssueかPRにコメントとして残す。**GitHub上に議論が残らないと、就活で見せられる材料が減る。**

## 9. テスト戦略とCI

### 9-1. 3層のテスト

**第1層：単体テスト（画像不要の合成シーン）**

`tests/fixtures/synthetic_scene.py` に、**画像を一切使わない合成データ生成器**を置く。

```python
def make_scene(n_points=100, n_cameras=20, noise_px=0.0, seed=0):
    """3D点をランダム生成し、既知のカメラ行列で投影する。
    戻り値: (points_3d, cameras, observations_2d)  — すべて正解が既知
    """
```

これが Phase 2 の主力テストになる。重要な性質が3つある。

1. **画像処理を一切経由しない**ので、幾何アルゴリズムのバグだけを切り分けられる。
2. **陽太が10分で作れる**ので、相方のBlenderデータの完成を待たずに Phase 2 を開始できる。
3. `noise_px` を変えれば、**ノイズに対する頑健性が実験項目になる**。

対象：`geometry/dlt.py`、`geometry/triangulate.py`、`geometry/bundle.py`、`solvers/*`

ソルバのテストは解析的な正解と照合する（例：CG法は対称正定値な小行列に対して n 回以内に厳密解に到達する）。

**第2層：リファレンス回帰テスト**

引き継ぎ資料 §8 の方針どおり、OpenCV版と自作版の結果を許容誤差付きで照合する。

| 自作 | リファレンス |
|---|---|
| `geometry/dlt.py` | `cv2.solvePnP` |
| `geometry/triangulate.py` | `cv2.triangulatePoints` |
| `solvers/cg.py` | `scipy.sparse.linalg.cg` |

**Phase 0 でライブラリ版を先に作る最大の理由がこれ。** 正解が手元にあるとデバッグの難易度が桁で下がる。

**第3層：E2Eテスト**

`tests/data/` に置いた小さな合成データセット（低解像度・8枚程度、数MB以内）を通し、Hausdorff距離が閾値以下であることを確認する。CIで回せる軽さにする。

### 9-2. CI

**GitHub Actions で、push時に Ubuntu と Windows の2環境で `pytest` を実行。**

```yaml
# .github/workflows/ci.yml （骨子）
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
steps:
  - uses: actions/checkout@v4
  - uses: astral-sh/setup-uv@v3
  - run: uv sync
  - run: uv run pytest
```

**導入理由**

- **実利**：相方のWindowsで動かないコードに陽太が気づけない、という事故を自動で防ぐ。パス区切りと改行コードの問題が即座に出る。
- **就活**：CIバッジがREADMEに付いているリポジトリは、そうでないものと印象が違う。設定コストは1時間程度。

**Blender依存のテスト（`tools/blender_*.py`）はCIから除外する。** Blenderのインストールに時間がかかりすぎるため。これらは相方のローカルで手動確認とする。

## 11. 評価実験の設計

引き継ぎ資料 §7 Phase 4 を具体化し、2項目（E6・E7）を追加した。

| # | 実験 | 独立変数 | 従属変数 | 対応する数学・教科書 |
|---|---|---|---|---|
| **E1** | 画像枚数 vs 精度 | 5 / 10 / 20 / 40 枚 | Hausdorff距離、再投影誤差、点群密度 | — |
| **E2** | 撮影角度刻み vs 条件数 | 5° / 10° / 20° / 45° | **正規方程式の条件数**、奥行き方向の誤差 | T&B Lec. 12, 18 |
| **E3** | バンドル調整の効果 | 有 / 無 | カメラ角度誤差[deg]、再投影誤差[px] | Nocedal Ch. 10 |
| **E4** | 前処理の効果 | なし / Jacobi / ILU(0) | **CG法の反復回数**、計算時間 | Saad Ch. 6, 9–10 |
| **E5** | **手法比較（最重要）** | ①のみ / ④のみ / 統合 | Hausdorff距離、**穴の面積**、凹部の再現度 | 統合の妥当性の証明 |
| **E6** | **LMの減衰項 λ**（追加） | λ の初期値・更新則 | 収束回数、最終誤差 | **Tikhonov正則化 = 相原研の悪条件最小二乗** |
| **E7** | 実装方式（追加） | ループ / 行列演算 / Numba | 計算時間 | §7-5 の高速化方針 |

### 補足

**E2 が引き継ぎ資料 §4-2 の核心。** 「カメラ間の視差角が小さいと三角測量が悪条件化し、奥行き方向の誤差が横方向より桁で大きくなる」を、条件数という数字で説明する。角度刻みを振るだけで条件数と誤差が同時に動くので、実験として非常にきれいに出る。

**E5 には凹み形状を含む被写体が必須**（§2 参照）。凸形状だけで実験すると統合の意味が数字に出ない。

**E6 は引き継ぎ資料 §4-3 の「λ の選び方が収束性と精度を左右する構図は、相原研の悪条件最小二乗そのもの」を実験化したもの。** 研究室訪問・院試で最も語りやすい実験になる。

**E1・E2・E3・E5 は合成データ（真値メッシュあり）で実施する。** 実写では Hausdorff 距離が測れないため、実写は「実環境でも動く」ことの実証に用いる。

## 15. 成果の語り口

引き継ぎ資料 §11 を維持しつつ、**相方側の語り口を追加**した。

### 就活面接（両者共通）

> 多視点復元は無地の面で点群が欠落し、シルエット法は凹形状を復元できないという相補的な弱点があります。そこで前者で推定したカメラ姿勢を後者の彫刻に流用し、さらに点群で凹部を補正する統合パイプラインを設計しました。単独手法との比較実験で、統合により表面誤差が○%改善することを確認しています。

### 開発手法について（両者共通）

> 3D復元は精度が実測しないと分からないため、最初の3週間を技術検証に充て、そこで得た再投影誤差の実測値をもとに要件を定義しました。以降は設計→実装→テストの工程を切って進めています。2人の作業を並行させるため、接続点となるファイル形式を最初のペアプログラミングで確定させ、それ以外はモジュール境界と担当境界を一致させることで、コンフリクトが構造的に起きない構成にしました。

### 共同開発について（両者共通・新規）

> 互いに専門が違うため、全コードに主担当と副担当を置き、副担当はレビュー時に「このPRが何をしているか」を自分の言葉で書くことを規約にしました。形式的な承認を防ぐためです。メッシュ平滑化の部分だけは、離散ラプラシアン行列の構成をCG担当が、それを解く共役勾配法を数理担当が実装し、2人で1つの数式を作りました。

### 陽太：研究室訪問・院試

> バンドル調整の縮小系をCG法で解く部分を自作し、前処理による反復回数の変化と、視差角が小さいときの条件数悪化を測定しました。Levenberg–Marquardt の減衰項はTikhonov正則化と形式的に同一なので、λ の選び方が収束性と精度に与える影響も実験項目に含めています。

### 相方：研究室訪問（新規）

> ボクセル空間から Marching Cubes でメッシュを起こしたあと、離散ラプラシアン作用素を用いた平滑化を実装しました。一様重みと cotan 重みで形状の歪み方が変わることを、真値メッシュとの Hausdorff 距離で定量的に比較しています。評価用のデータセットは Blender で自作し、カメラ行列と真値形状を既知としたうえで復元誤差を切り分けられるようにしました。
