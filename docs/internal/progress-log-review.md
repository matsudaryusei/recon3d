# 進捗ログのレビュー手順（AI向け）

**作成**: 2026-08-17
**対象**: `../progress.md`
**読む人**: このプロジェクトの進捗管理を担当するAI。メンバーは読まなくてよい。

---

## 役割分担

**AIは開発のサポート。開発そのものも、その記録も、メンバーがやる。**（2026-08-17・関口）

| | 誰が |
|---|---|
| 実装・コミット | **メンバー** |
| 進捗ログの記入・個人メモ | **メンバー** |
| **進捗の更新**（`../README.md` §1 の現在地、`../next.md` の「いまの状況」ブロック） | **AI** |
| `../next.md` の**状態列**（`⬜`→`🔄`→`✅`） | **メンバー**（本人がやった記録なので） |
| **`../../Discuss.md` への記述**（完了報告に不備があったとき） | **AI** |
| 記入されたログのレビュー（指摘のみ） | AI |

**AIの主業務はこの2つ（進捗の更新／Discuss.md への記述）。** それ以外のファイルに書き足すときは、メンバーの記録を奪っていないか一度確認する。

### ⛔ AIは進捗ログを書かない

**`../progress.md` への記入は、メンバーが行う。AIは1行も書き足さない。**（2026-08-17・関口の指示）

理由：ログは「実際にどう進んだか」の記録であり、**手を動かした本人しか書けない。** 詰まった点・工夫した点・振り返りを本人の言葉で残すことが目的なので（Discuss.md 08/17）、AIが埋めると記録として成立しない。

**AIがやるのは、書かれたものを読んで足りない項目を指摘することだけ。** 文面の提案を求められた場合も、**ログファイルを直接編集せず、会話の中で案を示すにとどめる。**

**同じ理由で `../next.md` の状態列と `../notes/` にも書かない。** どちらも「本人が何をやったか」の記録なので、AIが埋めると記録として成立しない。
**`../tasks/` の手順書については、[`ai-session-context.md` の「越えてはいけない線」](ai-session-context.md)を必ず読むこと**（実装や導出を書き足さない）。

### 呼ばれ方

メンバーが週次記録を書いたあと、進捗ログとこのファイルを渡して「レビューして」と言う。**書き足す前ではなく、書いたあとに走らせる。**

### 作業完了の報告を受けたとき

メンバーが「この作業が終わりました」と口頭・チャットで報告してきた場合（ログ記入とは別）、**成果物を実際に見て、不備があれば `../../Discuss.md` に書く。**（2026-08-17・関口の指示）

```markdown
### MM/DD

from Claude to <作成者>

（不備の内容。何が・計画書のどこと違うか・いつまでに直すか）
```

- **宛先は「作成者」。** 分からなければ `git log --format='%h | %an | %s'` でそのファイルのコミット作者を見る。**それでも判断できなければ関口に聞く。憶測で宛てない**
- 報告してきた人と作成者が別人のことがある（関口が全体の進捗としてまとめて報告する運用のため）
- **不備が無ければ何も書かない。** 「確認しました」だけの投稿で流れを埋めない
- 未着手のタスクは不備ではない。**書くのは「完成したと言われたものの中にある欠け」だけ**

### 指摘の出し方

- **多くても3件まで。** 全部指摘すると次から見せてもらえなくなる
- 各件は「**何が抜けているか / なぜ要るか（1行） / どこに何と書けばいいか**」の3点セット
- **書き方の細かさ（表記ゆれ・粒度）は指摘しない。** 判断に効かない
- 埋まっていない欄そのものは指摘対象ではない。**後の判断に使う欄が埋まっていないとき**だけ指摘する

## 1. 毎週見るもの

### 1-1. 歯止めの判定

累積表と当週の行から、以下に当たっていないか確認する。**当たっていたら必ず指摘する。**

| 状態 | 指摘する内容 |
|---|---|
| あるジャンルの実績が見積もりの **2倍**を超えた | そのジャンルに人を寄せるか、**スコープを削る**（計画書 §12 の撤退ライン） |
| **3週続けて誰も取らなかった**ジャンルがある | 前提知識が足りていないか優先度がずれている。**計画書 §3-7 の解説メモを先に入れる** |
| 週の実働合計が **12h を下回る**状態が3週続いた | 18週で終わらない。**期間延長（〜2027年2月）かスコープ削減の判断が要る** |
| 実績が見積もりの 1.5 倍以内 | 想定どおり。指摘しない |

見積もりにはデバッグ時間が入っていない（[決定記録 D-03](../decisions.md#d-03)）。**実績との比が出たら、残りの週の計画を直せる**ので、比が安定してきた時点で一度伝える。

### 1-1b. 文書の同期（30秒で見る）

**週次記録が書かれたとき、次の3つがズレていないかを見る。** ズレていたら1件として指摘してよい。

| 見るもの | 期待 |
|---|---|
| `../next.md` の状態列 | **進捗ログで「やった」と書かれたタスクが `✅` になっているか** |
| `../README.md` の §1（現在地） | 完了したジャンルの行が更新されているか |
| `../next.md` の「いまの状況」 | 週が進んでいるか |

**3つとも古い場合でも指摘は1件にまとめる。** 細かく分けて数を使わない。

### 1-2. 成果物として残っているか

**実測値・判断の根拠は、その週に書かないと二度と再現できない。** 以下が週の記述から読み取れるのに本書に無ければ指摘する。

- **測った数値**（処理時間・誤差・メモリ・件数）→ 節目の記録の表に入れる
- **口頭で決めたこと** → IssueかPRのコメントに1〜2行。毎日会えるぶん口頭で済みがちで、**GitHubに何も残らないと就活で見せる材料が減る**
- **計画書・決定記録を変えたのに「決定を変えた記録」が空** → [D-28](../decisions.md#d-28) は決定記録の改訂履歴と本書の**両方**に残す運用
- **詰まって解決した手順** → `docs/notes/` に1本。書き手は実装した本人（計画書 §8-3）

## 3. 記録を続けさせるための注意

- **週1の対面の場に紐付ける。** 単独タスクにすると続かない（[D-28](../decisions.md#d-28)）。記入が飛んだ週があっても遡って責めない
- 記録作業のコストは**週5〜10分**を上限と考える。それを超える指摘はしない
- **表を埋めることが目的ではない。** 「遅れているジャンルに人を寄せる」「見積もりを直す」という判断につながらない欄は、空のままでよい
- このファイルの観点が実態と合わなくなったら、**指摘するより先にこのファイルを直す**
