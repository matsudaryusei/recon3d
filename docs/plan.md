## 2. データ取得方針

### 決定：Blender合成データで着工し、Phase 0 最終週に実写を1セット通す

### 用語

- **レンダリング**: Blender内に3Dモデルを置き、仮想カメラから「写真を撮る」こと。出力は通常の画像ファイル。
- **真値メッシュ（ground truth mesh）**: 「正解の3D形状」。復元精度を測るための比較対象。
- **Hausdorff距離**: 2つの3D形状のズレの指標。「復元形状の各点から正解形状までの最大距離」。単位はmm。

### 合成データで得られるもの

Blenderに既知の3Dモデルを置き、カメラを円周上に20方向配置してレンダリングすると、以下が**全て正解付きで**手に入る。

| 出力 | 用途 |
|---|---|
| 画像 20枚 | パイプラインの入力 |
| **カメラ行列**（Blenderが知っている） | 姿勢推定（DLT・バンドル調整）の答え合わせ |
| **元の3Dモデル** | 真値メッシュ。Hausdorff距離の比較対象 |
| **シルエット画像** | セグメンテーションの答え合わせ |

> **→ 採用理由（真値が手に入る／デバッグが切り分けられる／今日から着工できる）と、却下した代替案: 決定記録 [D-01](decisions.md#d-01)**

### 既知のリスクと対策

**合成画像は綺麗すぎる。** ノイズも影のムラもなく特徴点が理想的に取れるため、実写に移った瞬間に精度が落ちる。

対策として、**Phase 0 の最終週（W3）に実写を1セットだけ通す**。精度は問わず、「自分たちの被写体で特徴点が何点取れるか」の実測値だけを取る。実写の本格導入は Phase 3（W12）から。

### 被写体の設計要件（重要）

> **必ず「凹んだ形状」を含む被写体を使うこと。合成データも同様。**

| 条件 | 失敗する手法 |
|---|---|
| 無地でテクスチャのない面 | ① 多視点復元（特徴点が取れず点群に穴が空く） |
| 凹んだ形状 | ④ シルエット復元（原理的に削れない） |

**マグカップはこの両方を満たす**（陶器の無地の面＋内側の凹み）。

> **→ なぜ凹みが必須なのか（最重要実験 E5 の成立条件）: 決定記録 [D-02](decisions.md#d-02)**

推奨する合成データセット：

| データセット | 目的 |
|---|---|
| `synthetic_cup` | 主データ。凹み＋無地面を持つマグカップ相当 |
| `synthetic_bunny` | 副データ。**①（多視点復元）が最も有利な条件**＝**テクスチャが豊富で、凹みが少ない**被写体。**①単独の上限性能の確認用** |

> ⚠️ **モデル名についての注意（2026-08-24 訂正）**：`synthetic_bunny` は**データセットの呼び名**であって、Stanford Bunny をそのまま使う指定ではない。
> **Stanford Bunny 自体は無彩色のスキャンデータでテクスチャを持たず、耳の間・顎の下に凹部もある。** そのまま使うと「①が最も有利な条件」にならないので、
> **テクスチャを別途貼るか、条件を満たす別のモデルを選ぶこと**（→ [T09](tasks/T09-find-3d-model.md)）。

### 3-1. 前提：工数は既に飽和している

| 項目 | 概算 |
|---|---|
| DLT・三角測量 | 30h |
| バンドル調整（Schur補元＋LM＋CG法） | 60h |
| ボクセル彫刻（行列化・高速化含む） | 25h |
| Marching Cubes | 20h |
| ラプラシアン平滑化 | 20h |
| 合成データ生成器 | 20h |
| セグメンテーション・特徴点 | 25h |
| テクスチャ投影・UV展開 | 25h |
| I/O・CLI・テスト・CI | 30h |
| 評価実験 | 40h |
| ドキュメント | 20h |
| **合計** | **315h** |

**この 315h は「何人でやるか」に依らない総量。** 人数で割ると1人あたりの負荷が出る。

| 人数 | 1人あたり週 | 備考 |
|---|---|---|
| 2人 | **8.75h** | 現状。引き継ぎ資料 §1 の想定（週6〜10時間）の範囲内 |
| 3人 | 5.8h | **増員するならこの線。** ただしレビューと同期のコストが増えるため、単純な割り算より少し悪くなる |
| 4人 | 4.4h | ジャンル数（§3-3 の9個）に対して細かく割りすぎる。**同じジャンルを複数人で持つ形になる** |

**ただしこの見積もりにデバッグ時間は含まれていない。** 数値計算のデバッグは実装の1〜2倍かかるのが普通であり、実質は450〜500h規模になりうる。超過分は §1 が許容する「余裕があれば5〜6か月」（〜2027年2月）で吸収し、それでも足りなければ §12 の撤退ラインで判定する。

**この制約から、「全てのコードを全員で書く」という運用は採れない。** だから「共有するかしないか」ではなく「**どこを、どの濃さで共有するか**」を設計する（§3-4）。

> **→ 根拠・試算・デバッグ時間の扱い: 決定記録 [D-03](decisions.md#d-03)・[D-04](decisions.md#d-04)**

<a id="s3-2"></a>
### 3-2. 分担の単位は「人」ではなく「ジャンル」

**事前に「誰がどのモジュールを持つか」を決めない。** §3-3 に**作業ジャンル**の一覧だけを置き、**その作業に着手する場面が来たときに、誰がやるかをその場で決める。**

| | 内容 |
|---|---|
| **事前に決めておくこと** | **どんな作業があるか**（ジャンル）、**何が前提知識か**、**いつ必要になるか**、**どのくらい重いか** |
| **その場で決めること** | **誰がやるか。** 1人でやるか、2人で分けるか、ペアで書くか |

**決め方**

1. **週1回の対面で、次週に着手するジャンルを見る**（§8-3 のIssue切りと同じ場）
2. **やりたい人が取る。** 手が挙がらなければ、前提知識が近い人が取る
3. **決まったらIssueに担当者とジャンルのラベルを付ける。** これが唯一の記録
4. **重いジャンルは分割してよい。** 「Marching Cubes のルックアップテーブルだけ」のような切り出しは歓迎

**固定しないことのほうが重要**

> **同じジャンルを同じ人が持ち続ける必要はない。** 週ごとに変わってよい。

- 得意・不得意の実像は、やってみるまで分からない
- **平日はほぼ毎日会えるため、その場の会話で「じゃあそこは自分がやる」と決まることが多くなる**（§3-4）。事前の表がその会話に勝つ理由はない
- **人が増えたときに、表を書き直さずに済む**

**規約：Approveコメントに要約を必須化する**

> PRのApproveコメントには、**「このPRが何をしているか、自分の言葉で1〜3行」**を必ず書く。

書けないなら、書けるまで質問する。対面で会えるので、その場で聞けばよい。**分担を固定しないぶん、「自分が書いていない部分を読む」機会がこの規約に集約される。**

> **→ 人からジャンルへ変えた理由: 決定記録 [D-36](decisions.md#d-36)・[D-09](decisions.md#d-09)**

<a id="s3-4"></a>
### 3-4. 共同作業の形

**前提：平日はほぼ毎日会える。相手が作業しているところを見ている時間が長い。**

この条件では、**「同席しているか」と「同じコードを書いているか」は別の軸**である。混同すると設計を誤るので、分けて考える。

#### 軸1：同席するか（`いつ・どこで`）

| | 内容 | throughput への影響 |
|---|---|---|
| **同席作業** ★既定 | **同じ場所で、各自が自分の作業をする。** 詰まったらその場で聞く。相手の画面が視界に入る | **ほぼゼロ。** 全員が自分の作業を進めているため |
| 非同席 | 各自の都合の時間に作業する | ゼロ |

**同席作業を既定とする。** これは費用がほぼ掛からないのに、質問の敷居が下がり、相手が何をしているかが自然に分かるという利点だけがある。**このプロジェクトで最も割の良い共同作業の形。**

#### 軸2：同じコードを書くか（`何を`）

| 濃さ | 形 | どこで使うか |
|---|---|---|
| **強** | **ペアプロ**。1つのコードを2人で書く | **下表の3か所のみ**（throughput が半分になるため） |
| 中 | **ジャンルを分けて書く。** 同じジャンル内でも「この関数はこっち」と切り分ける | **通常の運用**（§3-2・§3-3） |
| 弱 | レビューのみ | 前提知識の差が大きく、手が出しにくいところ |

**この2軸は独立している。** 同席していても、普段は各自が別のファイルを書いている（＝同席 × 中）。それが通常の姿。

> **→ 同席を既定にする根拠と、そこで生じる副作用: 決定記録 [D-29](decisions.md#d-29)**

**「強」（ペアプロ）に当たる箇所は3つだけ。**

| 箇所 | 想定時間 | 時期 |
|---|---|---|
| **`cameras.json` I/O と座標系変換** | 2h × 1回 | **W02**（W01 から持ち越し。→ [T01](tasks/T01-pairpro1-io.md)） |
| **ボクセル彫刻の行列化** | 2h × 2回 | W12 |
| **離散ラプラシアン `L` の構成と求解** | 2h × 3回 | W14 |

計12時間。総予算の約4%。**これ以上は増やせない。**

> **→ 3か所を選んだ理由・コスト比較・W01 が動かせない理由: 決定記録 [D-06](decisions.md#d-06)**

| 接続点 | なぜ重要か | 扱い |

| **`io/coords.py`（座標変換）** | ここを間違えると、**全ジャンルの出力が静かに壊れる**（§4） | **ペアプロで作る（W01）。** 以降、変換をここ以外に書いたらテストで落ちる |

<a id="s3-6"></a>
### 3-6. 運用ルール

1. **着手する前に、Issueに「ジャンル」と「担当者」を書く。** 同席していれば決めるのは口頭で足りるが、**決まった内容はIssueかPRのコメントに残す**（§8-3）。
2. **1つのIssueは1人が持つ。** 複数人で書くなら、**片方のブランチにコミットを積む**か、そこ宛に小さなPRを出す。`main` 宛のPRはIssueの担当者が出す。
3. **「これをやりたい」はいつでも言ってよい。** 週1の対面Issue切り（§8-3）を待つ必要もない。**入れ替えた事実だけ記録に残す。**
4. **手が空いたら、`Todo` から取る。** 「自分の担当ジャンルではないから待つ」という状態を作らない。
5. **前提知識が足りないジャンルを取ってもよい。** そのときは §3-7 の解説メモを先に1本読む／書いてもらう。

> **→ ジャンル単位にした理由と、そこで失うもの: 決定記録 [D-36](decisions.md#d-36)**

<a id="s3-7"></a>
### 3-7. 知識共有の仕組み

**分担を固定しないなら、知識の偏りを埋める仕組みが要る。** 対面で会えるため重い仕組みは不要。3つだけ。

1. **`docs/notes/` に短い解説メモ。** 前提知識のない人向け、A4半ページ程度。1本30分。**そのジャンルを最初に触った人が書く。**
   - 数理側の例：「SVDで `Ap=0` を解くとはどういうことか」「条件数とは何か」「なぜバンドル調整でSchur補元を使うのか」
   - 幾何・CG側の例：「cotan重みとは何で、なぜ一様重みより形が崩れないか」「UV展開とは何をしているか」「Marching Cubes の原理」「マスクの作り方」
   - **これは同時にREADMEと、外部に説明するときの下書きになる。**
2. **PRの説明文は、そのジャンルを知らない人が読む前提で書く。** §3-2 のApprove規約と対になる。
3. **月1回、自分が触っていないジャンルを1つ「説明してもらう」時間（30分）。** 理解の抜けが見つかる。

### 3-8. スコープの明示（新しく参加する人へ）

**先に知っておいてほしい線引き。** 「思っていたのと違う」を後から起こさないために書いてある。

| | 内容 |
|---|---|
| **やること** | **静止画の一括処理。** 写真20枚を入力し、カメラ位置を推定し、立体を復元し、精度を数値で測る |

<a id="s4"></a>
## 4. 座標系の規約

引き継ぎ資料 §10-5 が「事故が起きやすい」と警告した箇所。**規約を決めることより、規約を破れない構造を作ることが本質。**

<a id="s4-1"></a>
### 4-1. 決定：OpenCV規約に統一

| 対象 | 規約 |
|---|---|
| 世界座標系 | 右手系、**+Z が上**（ターンテーブルの回転軸）、原点は回転台の中心 |
| カメラ座標系 | **OpenCV規約**：+X 右、+Y 下、**+Z が光軸の前方** |
| 画像座標系 | **OpenCV規約**：原点は左上ピクセルの中心、+u 右、+v 下 |
| 外部パラメータの向き | **world → camera**。すなわち `X_cam = R · X_world + t` |

世界座標の「+Z 上」だけは Blender と揃える（Blenderも +Z 上の右手系）。これで**世界座標の変換は不要**になり、変換が必要なのはカメラ座標と画像座標だけになる。

> **→ OpenCV規約を選んだ理由・世界座標だけ Blender に揃える理由: 決定記録 [D-10](decisions.md#d-10)**

<a id="s4-2"></a>
### 4-2. Blender との変換

Blenderのカメラは **−Z 方向を見て、+Y が上**。OpenCVは **+Z 方向を見て、+Y が下**。Y軸とZ軸の符号が逆。

```python
C = np.diag([1.0, -1.0, -1.0])

R_cv = C @ R_blender
t_cv = C @ t_blender
```

画像の縦方向も逆（Blender/OpenGLは左下原点）：

```python
v_cv = H - 1 - v_blender
```

<a id="s4-3"></a>
### 4-3. 規約を破れなくする仕組み

> **`src/recon3d/io/coords.py` の中の関数以外では、座標変換を一切書かない。**

`diag(1,-1,-1)` や `H - 1 - v` が他のファイルに現れたら規約違反。機械的に検出する：

```python
# tests/test_conventions.py
def test_no_stray_coordinate_conversion():
    """io/coords.py 以外に座標変換のリテラルが現れないことを確認する。
    src/ 全体を走査し、diag(1, -1, -1) 相当のパターンを検出したら失敗。"""
```

**ペアプロ対象（§3-4）。**

> **→ なぜ規約ではなく構造で縛るのか・想定している事故の形: 決定記録 [D-11](decisions.md#d-11)**

## 5. `cameras.json` スキーマ

引き継ぎ資料 §10-3 で最優先とされた項目。①と④の唯一の接続点。

<a id="s5-1"></a>
### 5-1. スキーマ

```json
{
  "schema_version": "1.0",

  "convention": {
    "world_up": "+Z",
    "handedness": "right",
    "camera": "opencv",
    "image_origin": "top_left",
    "extrinsic_form": "world_to_camera"
  },

  "image_size": { "width": 1920, "height": 1080 },

  "intrinsics": {
    "fx": 1600.0, "fy": 1600.0,
    "cx": 960.0,  "cy": 540.0,
    "distortion": {
      "model": "opencv_radtan",
      "k1": 0.0, "k2": 0.0, "p1": 0.0, "p2": 0.0, "k3": 0.0
    }
  },

  "views": [
    {
      "image": "images/img_000.png",
      "mask":  "masks/img_000.png",
      "R": [[1,0,0],[0,1,0],[0,0,1]],
      "t": [0.0, 0.0, 0.5],
      "source": "turntable_gt",
      "turntable_angle_deg": 0.0,
      "reprojection_error_px": null
    }
  ],

  "meta": {
    "generated_by": "tools/blender_render.py",
    "generated_at": "2026-08-20T10:00:00+09:00",
    "dataset": "synthetic_cup_20views"
  }
}
```

<a id="s5-2"></a>
### 5-2. 各フィールドの役割

| フィールド | 役割 |
|---|---|
| `convention` ブロック | 規約をデータファイル自身に埋め込む。読み込み時に検証し、想定と違えば例外を投げる |
| `extrinsic_form` | `world→camera` かその逆かを文字列で持つ。`R` と `Rᵀ` の取り違えを防ぐ |
| **`source`** | `"turntable_gt"` / `"dlt"` / `"bundle_adjusted"`。**真値と推定値の切り替えがこの1フィールドで済み、下流のコードを変更せずに実験条件を切り替えられる** |
| `mask` | 画像・マスク・カメラ行列を `cameras.json` 1ファイルから全部たどれるようにする |

> **→ 各判断の根拠・`source` が撤退ラインの切り替えコストをゼロにしている件: 決定記録 [D-12](decisions.md#d-12)**

<a id="s5-3"></a>
### 5-3. 読み書きと検証

`src/recon3d/io/cameras.py` に、`dataclass` ベースの読み書き＋検証を置く。**pydantic等の追加依存は入れない**（→ [D-17](decisions.md#d-17)）。

検証項目：

| 項目 | 検出できる事故 |
|---|---|
| `schema_version` が既知か | 仕様変更の取り違え |
| `convention` が想定と一致するか | 規約違いのデータの混入 |
| `RᵀR ≈ I` | 回転行列の破損 |
| **`det(R) ≈ +1`** | **座標変換の符号ミス（−1なら鏡映）** |

<a id="s6-2"></a>
### 6-2. 骨格作りの範囲（W01・§13① の「ディレクトリ骨格を作成」）

**上のツリーは完成時の姿であり、W01 で全部作るものではない。** 骨格作りのゴールは**「空の器を置いて `uv run pytest` が通る状態にすること」**の1点とする。いまのボトルネックは `src/` も `tests/` も無いために `uv run pytest` が **exit code 5（テスト0件）**で終わることなので、ここが解消すれば骨格は完了と判定してよい。

**作るもの（これで全部）**

```
src/recon3d/__init__.py
src/recon3d/{io,geometry,solvers,vision,mesh,fusion,viz}/__init__.py
tests/test_import.py          # import recon3d するだけの smoke test
tests/fixtures/.gitkeep
tests/data/.gitkeep
tools/.gitkeep
docs/{notes,schema,experiments}/.gitkeep
```

- `__init__.py` は**空でよい**。中身を書くのは各ジャンルの担当週。
- `.gitkeep` を置くのは、**Git が空ディレクトリを追跡しない**ため。中身が入った時点で消してよい。
- **完了判定**：`uv sync` のあと `uv run pytest` が **`1 passed`（exit code 0）** で終わること。3台（Windows / Ubuntu / mac）で確認する（§13④）。

**作らないもの**

| 作らない | 理由 |
|---|---|
| `io/cameras.py`・`geometry/dlt.py` など**個別モジュールの空ファイル** | 着手時に「空ファイルを消して作り直す」無駄なコンフリクトが出る。ファイルは**担当週に、実装する人が作る**（`io/coords.py`・`io/cameras.py` は W01 ペアプロ#1、以降は §10 の週次カレンダーに従う） |
| **中身の実装** | 骨格は器だけ。実装は各ジャンルの作業 |
| `data/` 配下 | `.gitignore` の `/data/` で除外済み。**各自がローカルに作る**（`tests/data/` は除外対象外なのでコミットする） |
| `.github/workflows/ci.yml` | 骨格ではなく **G7**（§13②）の仕事 |

<a id="s6-3"></a>
### 6-3. `import recon3d` の通し方：プロジェクトをパッケージとして扱う

**`pyproject.toml` に `[build-system]` を足す**（2026-08-20 採用）。`uv sync` がプロジェクトを **editable install**（`src/` を編集したら即反映される形でインストール）するため、`import recon3d` がどこからでも通る。

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/recon3d"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

- ⚠️ **`packages = ["src/recon3d"]` の明示は必須。** `[project] name` が `4bitcom-HandM` でパッケージ名 `recon3d` と一致しないため、書かないと hatchling がビルド対象を見つけられず **`uv sync` が失敗する**。
- **採らなかった案**：pytest の `pythonpath = ["src"]` を張る方式。設定は1行で済むが、**通るのは pytest 実行中だけ**で、`uv run python tools/run_pipeline.py`（§6 の CLI エントリポイント）では `import recon3d` が通らない。**CLI を持つ計画なので採らない。**
- **`uv.lock` は1行変化する**（`source = { virtual = "." }` → `source = { editable = "." }`）。依存関係は増えないので、**この差分はコミットしてよい**。
- **他の端末は `git pull` のあと `uv sync` を1回流すこと**（editable install が入る）。
- ⚠️ **`src/recon3d/` が無い状態で先に `uv sync` してしまった端末は、`uv sync` だけでは直らない。** editable install が「中身なし」で固定され、以降の `uv sync` は `Audited` と言って再ビルドしない。**`uv sync --reinstall-package 4bitcom-handm` を1回流すこと**（`git pull` で `src/` ごと受け取る端末では起きない）。

> **→ この方式を選んだ理由・`pythonpath` 案を却下した理由: 決定記録 [D-38](decisions.md#d-38)**

| `uv run pytest` が `ModuleNotFoundError: No module named 'recon3d'` | 直前まで `1 passed` だったのに、数分後に落ちるようになった |
| 原因 | `uv` は `.venv` に macOS の **`hidden` フラグ**を付ける（正常）。**iCloud Drive がそのフラグを `.venv` 配下の全ファイルに伝播させ**、`site-packages/*.pth` まで hidden になった |
| なぜ import が壊れるか | CPython の `site.py`（`addpackage`）は **`hidden` が付いた `.pth` を読み飛ばす**。editable install のパスを教えるファイルが無視され、`src/` が `sys.path` に入らなくなる |
| 手で直せない | `chflags nohidden` で外しても、**1分ほどで iCloud が付け直す**（`.venv` 内 691 ファイルすべて） |
| 併発 | `.venv/lib 2` という **iCloud の衝突コピー**が生成されていた |

**対処**: リポジトリを `~/Projects/4bitcom` へ移動し、`.venv` を作り直した（`rm -rf .venv && uv sync`）。移動後は `hidden` 0 件、`uv run pytest` は `1 passed`。**`.git/` ごと移動するので remote 設定・追跡ブランチはそのまま生きる**（`git remote -v` と `git ls-remote` で確認済み）。

> ⚠️ **Windows の OneDrive も同じ罠がある**（`デスクトップ`・`ドキュメント` が既定で OneDrive 配下になっていることが多い）。**clone 先が同期フォルダでないかを最初に確かめること。**

## 8. ブランチ戦略とIssue運用

<a id="s8-1"></a>
### 8-1. ブランチ

**`main` のみを長期ブランチとする**（→ [D-22](decisions.md#d-22)）。

| 項目 | 決定 |
|---|---|
| `main` | 保護。直push禁止、PR必須 |
| ブランチ名 | `feat/<module>-<topic>` / `fix/<...>` / `docs/<...>` / `exp/<...>` |
| 例 | `feat/solvers-cg`、`feat/mesh-marching-cubes`、`exp/e2-angle-condition-number` |
| マージ | **squash merge に統一**（履歴が読みやすい。public化後に読まれる前提） |
| Approve | 他のメンバーのApprove必須。**ただし W1〜W2 は必須にせず、W3から必須化**（全員がGitに慣れるまで） |

<a id="s8-2"></a>
### 8-2. PRの規約

1. **PRの説明文は、相手の専門外を前提に書く。** 「何を」「なぜ」を1〜3段落。
2. **Approveコメントには「このPRが何をしているか、自分の言葉で1〜3行」を書く。** 形式的なLGTMを構造的に禁止する（§3-2）。
3. 1 PR = 1 Issue = 1トピック。複数のことを混ぜない。

<a id="s8-3"></a>
### 8-3. Issue の粒度

> **1 Issue = 1 PR = 1〜2週で終わる単位。**

Phase単位のIssue（例：「Phase 2 を完了する」）は作らない。

**ラベル**

| 種類 | 値 |
|---|---|
| **ジャンル（§3-3）** | `G1:数理コア` `G2:3DCG` `G3:画像処理` `G4:メッシュ` `G5:ボクセル統合` `G6:基盤IO` `G7:テストCI` `G8:実験可視化` `G9:ドキュメント` |
| フェーズ | `phase:0` 〜 `phase:4` |
| 特殊 | `pair`（ペアプロ対象）、`blocked`、`good-first-issue`（**新しく入った人向け**） |

**運用**

- GitHub Projects のボードを1枚：`Todo` / `In Progress` / `In Review` / `Done`
- **Issue には必ずジャンルのラベルを付ける。担当者（Assignee）は着手する時点で入れる**（§3-2）。**未着手のIssueに担当者が入っていないのは正常**
- **週1回、対面15分で次週分のIssueを切る。** 会えるという条件を活かす
- 対面で決めたことは、その場でIssueかPRにコメントとして残す。**GitHub上に議論が残らないと、後から「なぜこうしたか」が誰にも分からなくなる**

## 11. 評価実験の設計

引き継ぎ資料 §7 Phase 4 を具体化し、2項目（E6・E7）を追加した。

| # | 実験 | 独立変数 | 従属変数 | 対応する数学・教科書 |
|---|---|---|---|---|
| **E1** | 画像枚数 vs 精度 | 5 / 10 / 20 / 40 枚 | Hausdorff距離、再投影誤差、点群密度 | — |
| **E2** | 撮影角度刻み vs 条件数 | 5° / 10° / 20° / 45° | **正規方程式の条件数**、奥行き方向の誤差 | T&B Lec. 12, 18 |
| **E3** | バンドル調整の効果 | 有 / 無 | カメラ角度誤差[deg]、再投影誤差[px] | Nocedal Ch. 10 |
| **E4** | 前処理の効果 | なし / Jacobi / ILU(0) | **CG法の反復回数**、計算時間 | Saad Ch. 6, 9–10 |
| **E5** | **手法比較（最重要）** | ①のみ / ④のみ / 統合 | Hausdorff距離、**穴の面積**、凹部の再現度 | 統合の妥当性の証明 |
| **E6** | **LMの減衰項 λ**（追加） | λ の初期値・更新則 | 収束回数、最終誤差 | **Tikhonov 正則化と同じ構図（悪条件な最小二乗の扱い）** |
| **E7** | 実装方式（追加） | ループ / 行列演算 / Numba | 計算時間 | §7-5 の高速化方針 |
| **E8** | **レンダリング条件 vs 復元精度（候補）** | 照明配置 / シェーディング / 露出 / 背景 | マスクのIoU、特徴点数、Hausdorff距離 | G2 と G8 にまたがる。**採否は W04 に判断**（§16） |

### 補足

**E2 が引き継ぎ資料 §4-2 の核心。** 「カメラ間の視差角が小さいと三角測量が悪条件化し、奥行き方向の誤差が横方向より桁で大きくなる」を、条件数という数字で説明する。角度刻みを振るだけで条件数と誤差が同時に動くので、実験として非常にきれいに出る。

**E5 には凹み形状を含む被写体が必須**（§2 参照）。凸形状だけで実験すると統合の意味が数字に出ない。

**E6 は引き継ぎ資料 §4-3 の「λ の選び方が収束性と精度を左右する」という指摘を実験化したもの。** **なぜ収束したのか／しなかったのかを数値で説明できる**ようになるのが狙い。

**E1・E2・E3・E5 は合成データ（真値メッシュあり）で実施する。** 実写では Hausdorff 距離が測れないため、実写は「実環境でも動く」ことの実証に用いる。

## 15. 成果の語り口

引き継ぎ資料 §11 を維持しつつ、**松田側の語り口を追加**した。

### 就活面接（両者共通）

> 多視点復元は無地の面で点群が欠落し、シルエット法は凹形状を復元できないという相補的な弱点があります。そこで前者で推定したカメラ姿勢を後者の彫刻に流用し、さらに点群で凹部を補正する統合パイプラインを設計しました。単独手法との比較実験で、統合により表面誤差が○%改善することを確認しています。

### 開発手法について

> 3D復元は精度が実測しないと分からないため、最初の3週間を技術検証に充て、そこで得た再投影誤差の実測値をもとに要件を定義しました。以降は設計→実装→テストの工程を切って進めています。作業を並行させるため、接続点となるファイル形式を最初のペアプログラミングで確定させ、それ以外はモジュール境界と作業ジャンルの境界を一致させることで、コンフリクトが構造的に起きない構成にしました。

### 共同開発について（2026-08-16 改訂）

> 担当を人に固定せず、**作業を9つのジャンルに切って管理しました。** 誰がどれをやるかは、その作業に着手する時点で決めます。専門が違うメンバーでも、前提知識と重さをジャンルごとに明示しておけば、手が空いた人が取れるためです。全部を全員で書くと工数が足りないので、共同作業の濃さを「同じ画面で書く」「ジャンルを分けて書く」「レビューのみ」の3段階に分け、**事故が起きると全工程に波及する座標系の規約と、ジャンル間の接続点だけを最も濃い形（ペアプログラミング）で作りました。** レビューでは「このPRが何をしているか」を自分の言葉で書くことを規約にし、形式的な承認を防いでいます。

### 技術的な芯について

> バンドル調整の縮小系をCG法で解く部分を自作し、前処理による反復回数の変化と、視差角が小さいときの条件数悪化を測定しました。Levenberg–Marquardt の減衰項はTikhonov正則化と形式的に同一なので、λ の選び方が収束性と精度に与える影響も実験項目に含めています。ボクセル空間から Marching Cubes でメッシュを起こしたあとの平滑化では、離散ラプラシアンの重み（一様 vs cotan）で形状の歪み方がどう変わるかを、真値メッシュとの Hausdorff 距離で定量比較しました。評価用データセットは Blender で自作し、カメラ行列と真値形状を既知としたうえで、どこで誤差が入ったかを切り分けられるようにしています。
