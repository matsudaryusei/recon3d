2. 確定したテーマ#

一言でいうと#

物をぐるっと一周撮った写真から、3Dモデルを作るシステム。

内部で実際にやっていることは：

未知数のほうが式より多い（あるいは誤差で矛盾する）巨大で疎な連立方程式を、誤差が最小になるように反復法で解く

写真も3Dモデルも、その入口と出口にすぎない。

統合の対象#

元々の候補にあった以下2案を 統合 する。

  • ① 多視点画像からの3Dモデル自動生成（SfM系: 特徴点 → カメラ姿勢 → 三角測量 → 点群）
  • ④ シルエットからの物体形状復元（Visual Hull系: 輪郭抽出 → ボクセル彫刻 → メッシュ）

統合の論理（このプロジェクトの存在理由）#

2手法の弱点が 相補的 であることが根拠。

手法得意不得意
① 多視点復元テクスチャのある面、凹み部分無地の面、輪郭付近、点群が疎で穴が空く
④ シルエット復元外形が確実に取れる、必ず閉じた形状になる凹んだ部分を原理的に削れない、テクスチャ情報を使わない

合流点は2箇所:

  1. ④の「削る」処理には撮影角度（カメラ姿勢）が必須 → ①がこれを供給する
  2. ④は凹形状を削れない（お椀の内側が埋まる） → ①の点群が「ここは物体の内側ではない」と教えて補正する

→ 「2つやりました」ではなく「片方の欠点をもう片方で補う設計にしました」と説明できる。統合の必然性が語れる点が重要。

4. 数理的な芯（関口の担当領域）#

このテーマを採用した最大の理由。4つの計算核を意識的に自作範囲に確保している。

4-1. カメラ姿勢推定 — SVDによる同次最小二乗#

A p = 0 を ||p|| = 1 の制約下で解く。解は A の最小特異値に対応する右特異ベクトル。 → T&B で学んだSVDがそのまま実装対象になる。

4-2. 三角測量 — 線形最小二乗と条件数#

カメラ間の視差角が小さいと問題が悪条件化する。 奥行き方向の誤差が横方向より桁で大きくなる現象を、正規方程式の条件数で説明できる。 → 「撮影角度 vs 条件数 vs 復元誤差」がそのまま実験項目になる。

4-3. バンドル調整 — 悪条件な非線形最小二乗（最重要）#

再投影誤差の最小化：

min  Σ || π(R_i X_j + t_i) - x_ij ||²
  • Gauss-Newton の正規方程式 JᵀJ Δ = -Jᵀr を組むと、JᵀJ は疎なブロック構造を持つ
  • 3D点ブロックを Schur補元 で消去 → カメラのみの縮小系（対称正定値・疎）が残る
  • この縮小系をCG法で解く → Saad の実装がそのまま使える
  • Levenberg–Marquardt の減衰項 λI は形式的に Tikhonov正則化 と同一 → λ の選び方が収束性と精度を左右する構図は、相原研の悪条件最小二乗そのもの

4-4. メッシュ平滑化 — 疎ラプラシアン系#

(I + λL) x' = x を解く。L は疎対称行列。CG法 + 前処理の効果測定の題材。

最重要の設計方針：インターフェースで切る#

境界をファイル形式で定義する。 これが決まっていれば、お互いの実装完了を待たずに並行作業できる。

①→④ の依存関係の正確な把握#

①-a 特徴点マッチング     … CG担当
①-b カメラ姿勢推定       … ★④が必要とするのはここだけ
①-c 三角測量 → 点群      … 凹み補正でのみ使う
①-d バンドル調整         … 精度向上。なくても④は動く

④-a シルエット抽出       … ①と完全に独立
④-b ボクセル彫刻         … ①-b の出力が必要
④-c メッシュ化           … ①と独立

→ ④が待っているのは cameras.json という1ファイルだけ。

「①を完成させてから④」は採用しない（重要）#

理由:

  • 松田が6週間何もできない。2人プロジェクトとして致命的。GitHub履歴も片方だけになる。
  • ①-b が詰まった瞬間に全体が止まる（単一障害点）。

採用する組み方：モックによる分離#

ターンテーブルの回転角からカメラ姿勢は幾何的に計算できる。 これを cameras.json に書き出しておけば、④は①の完成を待たずに着工できる。

6. 撮影条件（スコープ制限）#

難易度を決めるのは実装よりも入力条件。以下を固定する。

  • ターンテーブル（回転台）+ 固定カメラ、10〜20°刻みで撮影
  • 単色背景（緑や黒の布）→ セグメンテーションが背景差分で済む
  • チェッカーボードで内部パラメータを事前較正 → 推定するのは外部パラメータのみ
  • 被写体は テクスチャのあるフィギュア・マグカップ程度。鏡面・透明物は除外
  • 照明固定

最大の利点#

ターンテーブルの回転角が真値（ground truth）になる。 推定したカメラ姿勢を真値と比較できるので、「なんとなくそれっぽい形が出た」ではなく 角度誤差 [deg] という定量評価ができる。他の候補テーマにはない強み。

7. 開発プロセス#

方針：PoC → ウォーターフォールの折衷#

純粋なウォーターフォールは不採用。理由は、このテーマでは 基本設計の妥当性が実装してみるまで検証できない ため（特徴点が十分取れるか、収束するか、再投影誤差がどの程度かは設計書に書けない）。3か月目に「精度が出ない」と判明すると挽回不能。

一方、SE/SIer系を併願に残すなら設計書・テスト仕様書を書いた経験は評価される。また2人の分担がインターフェース定義に依存するため、設計フェーズ自体には強い意味がある。

→ 不確実性の高い前半を探索的に、不確実性が減った後半をウォーターフォール的に。

フェーズ計画#

Phase 0：技術検証（3週間、ドキュメント最小）#

既存ライブラリを繋いで一直線に通す。OpenCVで特徴点、solvePnPで姿勢、triangulatePointsで点群、Open3Dで表示。

目的は「自分たちの撮影環境で特徴点が何点取れるか」「再投影誤差が何pxか」の実測値を得ることだけ。 数字が出ないなら被写体か照明を変える。

※ この段階で Blender内蔵Pythonのバージョンを確認 すること（§8参照）。

Phase 1：要件定義・基本設計（2週間）#

Phase 0 の実測値を根拠に数値目標を置く。

例: カメラ角度誤差 2°以下 / 再投影誤差 1.5px以下 / 処理時間 10分以内 / Hausdorff距離で真値メッシュとの誤差 ○mm以下

ファイルインターフェース仕様を確定。

Phase 2：数理コアの自作（6週間）#

DLT・三角測量・バンドル調整・CG法ソルバを自作し、Phase 0 のライブラリ版と結果を突き合わせる。 ライブラリ版が正解のリファレンスになるため、デバッグが劇的に楽になる。 これがPhase 0を挟むもう一つの理由。

Phase 3：Visual Hull統合とメッシュ化（4週間）#

ボクセル彫刻 → Marching Cubes → 平滑化 → テクスチャ → Blender出力

Phase 4：評価実験（3週間）#

  • 画像枚数 vs 復元精度（5/10/20/40枚）
  • 撮影角度刻み vs 三角測量の条件数 vs 誤差
  • バンドル調整の有無による精度差
  • CG法の前処理あり/なしでの反復回数・計算時間
  • ①のみ / ④のみ / 統合 の3条件比較 ← 統合の妥当性を数字で証明する最重要実験

8. 技術スタック（確定）#

使用言語：Python 単一言語#

確定理由:

  1. Blender が Python API しか受け付けない。 出口が固定されている以上、全体を揃えるのが最も摩擦が少ない。
  2. OpenCV / Open3D / scikit-image は全て Python ファースト。C++にすると松田の作業速度が落ちる。
  3. PRで相互レビューする設計上、片方が読めない言語が混ざるとレビューが形骸化する。

自作とライブラリの線引き#

レイヤ扱い
BLASレベル（行列積、ノルム、疎行列matvec）NumPy / SciPy に任せる
反復解法（CG法、前処理、収束判定）自作
最適化（Gauss-Newton、LM、Schur補元）自作
幾何アルゴリズム（DLT、三角測量、ボクセル彫刻）自作

A @ x を自作する意味はゼロだが、その上に載るCG法・LM法は完全に自作範囲。学部でも研究でも疎行列演算をBLAS/SpMVに乗せるのは普通であり、欠点にならない。

性能面の懸念と対処#

ボクセル彫刻が最大の負荷（256³ ≈ 1670万ボクセル × 20枚 = 3億回の投影）。

forループではなく行列演算として書く。 全ボクセル中心を 4×N の同次座標行列にまとめ、カメラ行列を左から一括適用する。

# ループで書く（× 数時間）
for v in voxels:
    for cam in cameras:
        p = cam.P @ v

# 行列で書く（○ 数秒）
uv = P @ V          # P: 3×4, V: 4×N

この書き換え自体が実験項目になる（ナイーブ実装との速度比較）。 逃げ道として Numba の @njit（デコレータ1行で10〜100倍）。

C++ / Rust を採用しない理由#

  • C++: CMake、Eigen、OpenCVビルド、2台のマシンの環境差 → 環境構築で2週間溶けるリスク。しかも結局Blender連携でPythonが必要。
  • Rust: この領域のエコシステムが薄い。Rustは別のCLIプロジェクトで示すほうが確実。

どうしても入れる場合の推奨: Phase 4 でプロファイリングし、最も重い1関数だけを pybind11 でC++化する。「ボトルネックを計測で特定し、該当箇所のみC++で置換して○倍高速化」のほうが全面C++より説明として強く、リスクも局所化される。

12. 検討したが採用しなかった案（再提案不要）#

案不採用の理由
物理シミュレーション × Unity数学的な芯（圧力ポアソン方程式のCG法）は優秀だが、Unityと数値計算部分の言語をまたぐ接続コストが高い。第二候補として残置。
画像復元・悪条件逆問題（CGLS + Tikhonov）研究接続は最高、完遂リスクも最低。ただし松田のCG専門が活きる範囲が狭い。共同開発である以上、松田が「自分の仕事」と感じられるかは無視できないため見送り。
ラプラシアン系の画像・メッシュ処理ソルバとしての難易度が一段低く、研究接続もやや弱い。
画像処理の自動最適化 / 画像の美しさの数理評価 / 避難・交通シミュレーション数理的な芯が細く、評価が主観に寄る。
