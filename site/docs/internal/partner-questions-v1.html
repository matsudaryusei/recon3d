Part 0. プロジェクトの30秒要約#

作るもの: 物を一周撮った写真から3Dモデルを作るシステム。

2つの手法を統合する。 それぞれの弱点が正反対だから。

手法得意不得意
① 多視点復元（特徴点→カメラ姿勢→点群）模様のある面、凹み無地の面（点群に穴が空く）
④ シルエット復元（輪郭→ボクセル彫刻→メッシュ）外形が確実、必ず閉じた形になる凹みが原理的に削れない（お椀の内側が埋まる）

合流点は2つ。

  1. ④が「削る」にはカメラの角度が要る → ①が供給する
  2. ④は凹みを削れない → ①の点群が「ここは物体の外だ」と教えて補正する

期間: 2026-08-17 着工 〜 12-20（18週）。1人あたり週8〜9時間。 言語: Python単一。Blender が Python API しか受け付けないため。 役割: 関口＝数値計算（カメラ姿勢推定・最適化・反復解法）、松田＝CG・画像処理・メッシュ・データ生成。

Part 1. 合意してほしいこと#

Q1. 君の「技術核」3つ、これで納得できるか？ 【最重要】#

正直に書く。最初の計画では、君の担当が「作業の受け皿」になっていて、3DCG研究への助走になっていなかった。 関口側は「悪条件最小二乗＝志望研究室のテーマ」に直結する部分を4つ確保していたのに対して、君側にそれに相当するものが無かった。片方だけが得をする構造で、これは共同開発として良くない。

そこで、君側にも研究につながる技術核を3つ確保した。

核1：合成データセット生成器（Blender）

Blenderに既知の3Dモデルを置き、カメラを円周上に20方向並べてレンダリング。画像・シルエット・カメラ行列・正解の3D形状を一括出力する。着工1週目から君が主役になる部分。

核2：メッシュ処理（Marching Cubes 以降）

ボクセル（3Dのピクセル）の塊からメッシュを起こし、簡略化・UV展開・テクスチャ投影まで。

核3：離散ラプラシアン作用素の構成（関口と共同）

メッシュを滑らかにする処理で (I + λL) x' = x という方程式を解く。この L という行列の作り方を君が担当する。

担当内容分野
君行列 L の構成。一様重み vs cotan重み（三角形の角度から決まる重み）を両方実装し、形の歪み方の違いを測る離散微分幾何
関口できた疎行列を共役勾配法で解く。反復回数・収束を測る数値線形代数

核3が一番大事だと思っている。 ここが2人の専門が実際に交わる唯一の点で、「分担して2つ作った」ではなく「同じ数式を、幾何側と解析側から2人で作った」と言える。就活でも研究室訪問でも、この1点があるかないかで話の強さが変わる。

【これが変わる】 Noなら役割分担を組み直す。何が足りないかを具体的に教えてほしい。

Q2. このプロジェクトにリアルタイム描画は登場しない。了承できるか？ 【最重要】#

君の興味は「リアルタイム・Unity・GUI寄り」と聞いた。正直に言うと、このプロジェクトは静止画の一括処理で、リアルタイム描画は本質的に出てこない。 Unityも、数値計算部分との言語をまたぐ接続コストが高いため不採用にしてある。

だから君の旨味は、リアルタイム描画ではなくジオメトリ処理とレンダリングに置くことになる。 3DCG研究の評価軸としてはジオメトリ処理のほうがむしろ王道ではあるが、君がやりたいことと違うなら意味がない。

受け皿として用意してあるもの: ボクセルが削られていく過程をリアルタイム表示するビューア。デモ動画として一番見栄えがする部分でもある。ただし優先度は最後（余力があれば）。

【これが変わる】 「どうしてもリアルタイム描画を主軸にしたい」なら、このテーマ自体を再検討したほうがいい。第二候補として「物理シミュレーション × Unity」という案が残してある。着工前なら乗り換えのコストはゼロだが、着工後だと全部が無駄になる。今言ってほしい。

回答:
□ 了承する。ジオメトリ処理で問題ない
□ 了承するが、ビューアは優先度を上げたい
□ リアルタイム描画を主軸にしたい（テーマ再検討）

Q3. 「主担当＋副担当」という進め方でいいか？#

「二人で協力して作りたい」という話があったので、その形を設計した。ただし全部を2人で書くと開発速度が半分になり、確実に間に合わない（工数計算済み・後述）。そこで折衷案。

役割やること
主担当実装する。設計判断をする
副担当PRをレビューする。「何をやっているか説明できる」ところまで理解する。 実装はしない

つまり全てのコードに、書く人と読む人がいる。 書く1人＋読む1人なら消費は1.3倍程度で済むが、書く2人だと2倍になる。工数からしてこれが上限。

⚠ この設問は 2026-08-15 に修正された#

「副担当は実装しない」は書き方の誤りだった。 実際に想定しているのは「詳しいほうが主軸になって、一緒に作る」形であり、副担当も実装に参加する。

修正版（第2版 Q-e）に松田は「了承」と回答済み（2026-08-16）。 ただしこの「主担当＋副担当」という枠組み自体が同日にジャンル制へ改訂された（→ D-36）。上の表は経緯の記録として残してある。

修正後の定義（計画書 §3-2・§3-6 が正典）:

役割やること
主担当設計を決める。 モジュールの中核を実装する。副担当がやる部分を切り出す
副担当切り出された部分を実装する。 そのうえでPR全体をレビューして理解する

切り出しの原則は「副担当自身の専門が顔を出す部分を選ぶ」。具体的な割り当ては計画書 §3-6 の担当表を参照。

あわせて1つルールを入れたい。

PRを承認するとき、コメントに「このPRが何をしているか、自分の言葉で1〜3行」を必ず書く。

「LGTM」だけの形式的な承認を構造的に禁止するため。書けないなら、書けるまで聞く。よく会えるので、その場で聞けばいい。

これは就活でも効く。「相互レビューで互いの専門を理解した」を、GitHubのPR履歴という証拠付きで語れる。

Q5. 「合成データから始める」方針でいいか？#

最初は実物を撮影せず、Blenderの中でレンダリングした画像から始めたい。

理由は3つ。

① 正解が全部手に入る。 実物を撮影しても、そのマグカップの「正しい3D形状」は誰も知らない。だから復元結果が正しいかを数値で言えない。Blenderなら、元の3Dモデルがそのまま正解になる。カメラの位置も、シルエットも、全部正解が分かる。

② デバッグが劇的に楽になる。 誤差ゼロの完璧な入力を入れて答えが合わなければ、原因は100%プログラムのバグ。実物だと「バグなのか撮影が悪いのか」が切り分けられず、ここで数週間溶ける。

③ 今日から始められる。 回転台も背景布も照明も要らない。そして君の最初の仕事が1週目に発生する（関口の実装完了を待たなくていい）。

実物撮影は Phase 0 の最終週（W03、8/31の週）に1セットだけ試して感触を掴み、本格導入は Phase 3（11月）から。

【これが変わる】 「最初から実物でやりたい」なら、機材調達を最優先タスクにして日程を組み直す。

ここから判明した重要な制約：Cycles は CPU レンダリングになる#

システム情報の Cycles の欄に出ているのは CPU device capabilities: AVX2 の1行だけで、GPU 計算デバイス（OneAPI 等）が挙がっていない。 つまり現状の設定では Cycles を選ぶとレンダリングが CPU で回る。

ボクセル解像度の試算（メモリ回答待ちの理由）#

256³ = 1677万ボクセル。占有グリッド自体は小さい（uint8 なら 17 MB）が、問題は §7-5 の「行列で一括投影する」実装のほうで、中間バッファが大きくなる。

配列256³128³
占有グリッド（uint8）17 MB2 MB
全ボクセル中心の同次座標 4×N（float64）537 MB67 MB
投影結果 3×N（float64・カメラ1台分）403 MB50 MB

素直に書くと 256³ で一時的に 1 GB 前後を使う。メモリ 8 GB だと厳しく、16 GB なら（チャンク分割すれば）通る、という線。

対応方針: どちらに転んでも動くよう、ボクセルをチャンク（塊）に分割して投影する実装を最初から採る。 これは関口側（geometry/carving.py、ペアプロ#2）の設計に落とす。そのうえで解像度の最終決定は W12 に実測で行う。

なのでメモリ容量だけは早めに教えてほしい（Win + Pause キー、またはタスクマネージャー → パフォーマンス → メモリ）。

Q18. 合成データの元にする3Dモデル 【W01】#

君が Blender で用意する最初のデータ。条件が1つある。

必ず「凹んだ形状」を含むモデルにすること。

理由: このプロジェクトの最重要実験は「①のみ / ④のみ / 統合」の3条件比較で、統合が優れていることを数字で証明するもの。ところが凸形状（球、Suzanne など）だけだと、シルエット法が苦手とする凹みが存在しないので、統合の意味が数字に出ない。

理想は「無地の面 + 凹み」の両方を持つもの。

条件失敗する手法
無地・模様がない面① 多視点復元（特徴点が取れず点群に穴が空く）
凹んだ形状④ シルエット復元（原理的に削れない）

マグカップがこの両方を満たす（陶器の無地の面＋内側の凹み）。だから主データはマグカップ相当を推したい。

副データとして Stanford Bunny のような凸・高テクスチャのモデルも1つ欲しい（①単独の上限性能を見るため）。
