T11：EEVEE は Object Index パス非対応／①アルファ方式の実測 2026/10/08#

T11（マスク生成方式を決める） のステップ2「EEVEE で ID Mask が動くか」を実機で確認した。 結論：EEVEE では ID Mask 方式は成立しない。 mask-options.md が「情報源によって『長らく非対応』『対応済み』で記述が割れている」として残していた宿題に、この環境での答えが出た。

これは判断材料であって決定ではない。 採用方式の決定（D-43）は2人で行う。下の「T11 の決定に与える影響」に分岐だけ整理してある。

症状#

tools/blender_id_mask_check.py の scene.render.engine を "CYCLES" → "BLENDER_EEVEE" に1行変えて実行したところ、ステップ4のソケット存在チェックで落ちた。

KeyError: "'Object Index' 出力ソケットが見つかりません。
利用可能な出力: ['Image', 'Alpha', 'Depth', ..., 'Object Index', 'Material Index', ...]

メッセージが矛盾している。 「見つかりません」と言いながら、同じ文の「利用可能な出力」に Object Index が載っている。 ここで「スクリプトのバグでは？」と疑ったが、ガードは本物の非対応を正しく捕まえていた。

切り分け（エンジンだけを変えた A/B）#

同じ .blend・同じコード経路で、scene.render.engine だけを変えて比較した。

use_pass_object_index の読み戻し"Object Index" in rl.outputsソケットの enabledenabled なソケット
CyclesTrueTrueTrueImage, Alpha, Object Index, Noisy Image
EEVEETrueFalseFalseImage, Alpha

EEVEE では Object Index パスが出ない。 紛らわしかったのは次の2点である。

#紛らわしかった点実際の挙動
1view_layer.use_pass_object_index = True が EEVEE でもエラーにならず、読み戻すと True になる代入は黙って受け取られるだけで、パスは出力されない。この属性は対応状況の判定に使えない
2出力ソケット Object Index は一覧には存在するのに、キー照合では見つからないソケットは enabled=False で存在している。[o.name for o in outputs] の反復は無効ソケットも拾うが、in / .get() / [...] のキー照合は無効ソケットに一致しない（3つとも失敗することを確認）

2 がそのまま、あの「あるのに無い」メッセージの正体である。 対応状況を判定したいときに見るべきは、属性の読み戻しでもソケット名の一覧でもなく、ソケットの enabled である。

副産物：EEVEE で使える代替パス#

同じ probe で、代替案（mask-options.md の比較表 の ①③）の足場も確認できた。

  • ①アルファ方式：Alpha ソケットは EEVEE でも enabled=True。scene.render.film_transparent = True も問題なく通る
  • ③Cryptomatte：view_layer.use_pass_cryptomatte_object = True にすると CryptoObject00〜CryptoObject02 が enabled=True になる

つまり EEVEE 単独で進めたい場合の代替は2つとも実在する。 ①については下の「①アルファ方式の実測」でマスクを実際に出力して測った（③Cryptomatte はパスが出ることの確認のみで、出力の実測は未実施）。

T11 の決定に与える影響#

「ID Mask を採用」のままでは済まなくなった。mask-options.md の「推す案と、その理由」 が想定していたとおりの分岐に入る。

案中身効く点痛い点
A: ID Mask ＋ マスクだけ Cycles推す案を維持し、カラー画像は EEVEE・マスクは Cycles で出す厳密に二値（[0. 1.]）＝質問2 に最強。1回のレンダーで、遮蔽を解いた物体別マスクが出る＝質問3 も満たすD-19 と衝突（決定文書の整合として改訂が必要）。パイプラインが2エンジン立てになり、T07 で6通りに壊れた Blender 5.0 コンポジタ API を踏み続ける
B: ①アルファ方式film_transparent ＋ numpy でしきい値EEVEE 単独で完結し D-19 を動かさずに済む。実装2〜3行でコンポジタを一切使わない。しきい値は実測で極めて鈍感（下記）厳密な二値ではない（輪郭1px に中間値、全体の 0.317%）。全オブジェクトの和集合しか出せず、物体別が要るなら1視点あたり 1 + N 回レンダーが必要
C: ③CryptomatteEEVEE でもパスは出るエンジンを跨いでも同じ書き方が通る実装が数十行。かつ輪郭がアンチエイリアスされるので結局しきい値が必要＝A の長所も B の手軽さも取れない

レンダー時間は決め手にならない（実測は下記）。案A を「CPU Cycles だから遅い」で落とすのは誤りで、マスクだけを samples=1 で焼けば40枚で追加4分に収まる。D-19 の「現実的な時間に収まらない」は大域照明つきの本番カラーレンダーと反復試行についての判断であり、マスクパスには当てはまらない。衝突するのは決定文書の整合であって、スループットではない。

実測後、論点は質問2 から質問3 に移った。 質問2（しきい値なしで二値）は、A が厳密に満たす一方、B も「中間値は輪郭1pxだけ・しきい値は鈍感」と分かったので実害がほぼない。残る本当の差は質問3（物体を分離できるか）である。

  • 合成シーンに被写体が1つだけなら（T12 は「シーンに被写体が1つ、原点に立っている」前提で .blend を整える）、B の「和集合しか出せない」はコストゼロ。回転台は合成データではモデリングしなければ写らないので、質問3 の「回転台＋被写体の2物体」は合成データでは回避できる
  • 逆に、回転台を含めて写す／被写体を複数置く設計にするなら、A が明確に優位（1回のレンダーで遮蔽込みの物体別マスク）

したがって T11 の決定は、T12 の「合成シーンに何を置くか」と連動する。 単体被写体で進めるなら B、シーンに回転台や複数物体を入れるなら A、という対応になる。

質問3：物体を分離できるか → できない（和集合になる）#

同一条件で、オブジェクトを1つずつ hide_render して分解した。

レンダー内容白の割合（threshold=0.5）
全部（円 ＋ 円.001）28.734%
円 のみ14.317%
円.001 のみ20.590%
（単体の和）34.907%

単体の和（34.907%）が全部（28.734%）を上回るのは、2物体が重なっている（遮蔽がある）ため。 そして単体マスクの和集合と「全部」の画素単位の一致率は 100.0000% だった。アルファ出力はシーン内の全オブジェクトのシルエットの和集合そのもので、物体の区別という概念を持たない。

物体別マスクが必要なら、他の物体を hide_render して焼き直すしかなく、1視点あたり 本番1回 + 物体数N回のレンダーになる。

ここが T07 の実測値との食い違いの正体でもある。 T07 の ID Mask は 円=6.380% だが、アルファで 円 単体を測ると 14.317%。ID Mask は「見えている部分」だけを返す（遮蔽が解かれている）ので、円 は 円.001 の陰に半分以上隠れていたことになる。これは A の長所である（1回のレンダーで遮蔽込みの物体別マスクが取れる）。 なお T07 の可視分の合計 26.793% と、アルファの和集合 28.734% には約1.9ポイントの差が残る。Cycles と EEVEE のカバレッジ差と、ID Mask の Anti-Alias オフによる中心サンプル判定（面積を小さめに見積もる）が原因と考えられるが、ここは詰めていない。方式選定には影響しない。

学んだこと・次に活かせること#

  • 「対応していない機能」は、エラーではなく黙った無効化として現れることがある。 use_pass_object_index = True は EEVEE でも通り、読み戻しても True が返る。書けたこと・読み戻せたことは、効いていることの証明にならない。 効いたかどうかは別の観測点（ここではソケットの enabled）で確かめる
  • bpy_prop_collection のキー照合は無効な要素に一致しない。 in が False なのに [o.name for o in ...] には載る、という食い違いが起きる。存在チェックが矛盾した結果を返したら、まず「無効な状態で存在している」を疑う
  • T07 の学び「エラーメッセージに候補一覧を出させる」は、今回半分だけ効いた。 一覧は出たが、enabled を出していなかったため「あるのに無い」で手が止まった。一覧を出すときは、名前だけでなく「使えるかどうか」も併記すると、次の人が1分で分かる。具体的には blender_id_mask_check.py:68-72 をこう直せる：
  sock = next((s for s in render_layers.outputs if s.name == "Object Index"), None)
  if sock is None or not sock.enabled:
      enabled = [s.name for s in render_layers.outputs if s.enabled]
      raise KeyError(
          f"'Object Index' が使えません（存在={sock is not None} / "
          f"enabled={getattr(sock, 'enabled', None)}）。"
          f"エンジン {scene.render.engine} はこのパスに非対応の可能性があります。"
          f"このエンジンで使える出力: {enabled}"
      )
  • 「弱点」は、大きさを測るまで弱点と決まらない。 今回 A/B の比較は、測る前と後で結論が引っくり返りかけた。B の「しきい値処理が必須」は実測すると 0.1〜0.9 で結果が 0.159 ポイントしか動かない＝ほぼ無害だったし、A の「CPU Cycles は遅い」も マスクパスなら40枚で4分＝無害だった。代わりに、測る前は誰も挙げていなかった「アルファは物体を分離できない」が最大の争点として残った。 比較表の定性的な○×は、採用の直前に必ず数字にする
  • レンダーエンジンの一覧を bl_rna.properties['engine'].enum_items で取ろうとしたのは誤りだった。 このenumは動的で、Cycles のような登録エンジンが列挙されない（最初の probe は ['BLENDER_EEVEE'] だけを返し、Cycles が無いビルドだと誤認しかけた）。エンジンの有無は scene.render.engine に代入して例外を見るか、addon_utils.check("cycles") で確かめる
