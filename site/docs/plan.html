2. データ取得方針#

決定：Blender合成データで着工し、Phase 0 最終週に実写を1セット通す#

用語#

  • レンダリング: Blender内に3Dモデルを置き、仮想カメラから「写真を撮る」こと。出力は通常の画像ファイル。
  • 真値メッシュ（ground truth mesh）: 「正解の3D形状」。復元精度を測るための比較対象。
  • Hausdorff距離: 2つの3D形状のズレの指標。「復元形状の各点から正解形状までの最大距離」。単位はmm。

合成データで得られるもの#

Blenderに既知の3Dモデルを置き、カメラを円周上に20方向配置してレンダリングすると、以下が全て正解付きで手に入る。

出力用途
画像 20枚パイプラインの入力
カメラ行列（Blenderが知っている）姿勢推定（DLT・バンドル調整）の答え合わせ
元の3Dモデル真値メッシュ。Hausdorff距離の比較対象
シルエット画像セグメンテーションの答え合わせ

→ 採用理由（真値が手に入る／デバッグが切り分けられる／今日から着工できる）と、却下した代替案: 決定記録 D-01

既知のリスクと対策#

合成画像は綺麗すぎる。 ノイズも影のムラもなく特徴点が理想的に取れるため、実写に移った瞬間に精度が落ちる。

対策として、Phase 0 の最終週（W3）に実写を1セットだけ通す。精度は問わず、「自分たちの被写体で特徴点が何点取れるか」の実測値だけを取る。実写の本格導入は Phase 3（W12）から。

被写体の設計要件（重要）#

必ず「凹んだ形状」を含む被写体を使うこと。合成データも同様。

条件失敗する手法
無地でテクスチャのない面① 多視点復元（特徴点が取れず点群に穴が空く）
凹んだ形状④ シルエット復元（原理的に削れない）

マグカップはこの両方を満たす（陶器の無地の面＋内側の凹み）。

→ なぜ凹みが必須なのか（最重要実験 E5 の成立条件）: 決定記録 D-02

推奨する合成データセット：

データセット目的
synthetic_cup主データ。凹み＋無地面を持つマグカップ相当
synthetic_bunny副データ。①（多視点復元）が最も有利な条件＝テクスチャが豊富で、凹みが少ない被写体。①単独の上限性能の確認用

⚠️ モデル名についての注意（2026-08-24 訂正）：synthetic_bunny はデータセットの呼び名であって、Stanford Bunny をそのまま使う指定ではない。 Stanford Bunny 自体は無彩色のスキャンデータでテクスチャを持たず、耳の間・顎の下に凹部もある。 そのまま使うと「①が最も有利な条件」にならないので、 テクスチャを別途貼るか、条件を満たす別のモデルを選ぶこと（→ T09）。

3-2. 分担の単位は「人」ではなく「ジャンル」#

事前に「誰がどのモジュールを持つか」を決めない。 §3-3 に作業ジャンルの一覧だけを置き、その作業に着手する場面が来たときに、誰がやるかをその場で決める。

内容
事前に決めておくことどんな作業があるか（ジャンル）、何が前提知識か、いつ必要になるか、どのくらい重いか
その場で決めること誰がやるか。 1人でやるか、2人で分けるか、ペアで書くか

決め方

  1. 週1回の対面で、次週に着手するジャンルを見る（§8-3 のIssue切りと同じ場）
  2. やりたい人が取る。 手が挙がらなければ、前提知識が近い人が取る
  3. 決まったらIssueに担当者とジャンルのラベルを付ける。 これが唯一の記録
  4. 重いジャンルは分割してよい。 「Marching Cubes のルックアップテーブルだけ」のような切り出しは歓迎

固定しないことのほうが重要

同じジャンルを同じ人が持ち続ける必要はない。 週ごとに変わってよい。

  • 得意・不得意の実像は、やってみるまで分からない
  • 平日はほぼ毎日会えるため、その場の会話で「じゃあそこは自分がやる」と決まることが多くなる（§3-4）。事前の表がその会話に勝つ理由はない
  • 人が増えたときに、表を書き直さずに済む

4. 座標系の規約#

引き継ぎ資料 §10-5 が「事故が起きやすい」と警告した箇所。規約を決めることより、規約を破れない構造を作ることが本質。

4-1. 決定：OpenCV規約に統一#

対象規約
世界座標系右手系、+Z が上（ターンテーブルの回転軸）、原点は回転台の中心
カメラ座標系OpenCV規約：+X 右、+Y 下、+Z が光軸の前方
画像座標系OpenCV規約：原点は左上ピクセルの中心、+u 右、+v 下
外部パラメータの向きworld → camera。すなわち X_cam = R · X_world + t

世界座標の「+Z 上」だけは Blender と揃える（Blenderも +Z 上の右手系）。これで世界座標の変換は不要になり、変換が必要なのはカメラ座標と画像座標だけになる。

→ OpenCV規約を選んだ理由・世界座標だけ Blender に揃える理由: 決定記録 D-10

4-2. Blender との変換#

Blenderのカメラは −Z 方向を見て、+Y が上。OpenCVは +Z 方向を見て、+Y が下。Y軸とZ軸の符号が逆。

C = np.diag([1.0, -1.0, -1.0])

R_cv = C @ R_blender
t_cv = C @ t_blender

画像の縦方向も逆（Blender/OpenGLは左下原点）：

v_cv = H - 1 - v_blender

4-3. 規約を破れなくする仕組み#

src/recon3d/io/coords.py の中の関数以外では、座標変換を一切書かない。

diag(1,-1,-1) や H - 1 - v が他のファイルに現れたら規約違反。機械的に検出する：

# tests/test_conventions.py
def test_no_stray_coordinate_conversion():
    """io/coords.py 以外に座標変換のリテラルが現れないことを確認する。
    src/ 全体を走査し、diag(1, -1, -1) 相当のパターンを検出したら失敗。"""

ペアプロ対象（§3-4）。

→ なぜ規約ではなく構造で縛るのか・想定している事故の形: 決定記録 D-11

pyproject.toml に [build-system] を足す（2026-08-20 採用）。uv sync がプロジェクトを editable install（src/ を編集したら即反映される形でインストール）するため、import recon3d がどこからでも通る。

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/recon3d"]

[tool.pytest.ini_options]
testpaths = ["tests"]
  • ⚠️ packages = ["src/recon3d"] の明示は必須。 [project] name が 4bitcom-HandM でパッケージ名 recon3d と一致しないため、書かないと hatchling がビルド対象を見つけられず uv sync が失敗する。
  • 採らなかった案：pytest の pythonpath = ["src"] を張る方式。設定は1行で済むが、通るのは pytest 実行中だけで、uv run python tools/run_pipeline.py（§6 の CLI エントリポイント）では import recon3d が通らない。CLI を持つ計画なので採らない。
  • uv.lock は1行変化する（source = { virtual = "." } → source = { editable = "." }）。依存関係は増えないので、この差分はコミットしてよい。
  • 他の端末は git pull のあと uv sync を1回流すこと（editable install が入る）。
  • ⚠️ src/recon3d/ が無い状態で先に uv sync してしまった端末は、uv sync だけでは直らない。 editable install が「中身なし」で固定され、以降の uv sync は Audited と言って再ビルドしない。uv sync --reinstall-package 4bitcom-handm を1回流すこと（git pull で src/ ごと受け取る端末では起きない）。

→ この方式を選んだ理由・pythonpath 案を却下した理由: 決定記録 D-38

7-8. リポジトリを同期フォルダの下に置かない【2026-08-20 追加】#

iCloud Drive / OneDrive / Dropbox / Google Drive の同期フォルダ配下に clone しないこと。 ローカルの作業ディレクトリに置く（例：~/Projects/4bitcom）。同期は Git がやるので、ファイル同期サービスは不要どころか有害。

実際に起きたこと（2026-08-20・mac）

現象中身
uv run pytest が ModuleNotFoundError: No module named 'recon3d'直前まで 1 passed だったのに、数分後に落ちるようになった
原因uv は .venv に macOS の hidden フラグを付ける（正常）。iCloud Drive がそのフラグを .venv 配下の全ファイルに伝播させ、site-packages/*.pth まで hidden になった
なぜ import が壊れるかCPython の site.py（addpackage）は hidden が付いた .pth を読み飛ばす。editable install のパスを教えるファイルが無視され、src/ が sys.path に入らなくなる
手で直せないchflags nohidden で外しても、1分ほどで iCloud が付け直す（.venv 内 691 ファイルすべて）
併発.venv/lib 2 という iCloud の衝突コピーが生成されていた

対処: リポジトリを ~/Projects/4bitcom へ移動し、.venv を作り直した（rm -rf .venv && uv sync）。移動後は hidden 0 件、uv run pytest は 1 passed。.git/ ごと移動するので remote 設定・追跡ブランチはそのまま生きる（git remote -v と git ls-remote で確認済み）。

⚠️ Windows の OneDrive も同じ罠がある（デスクトップ・ドキュメント が既定で OneDrive 配下になっていることが多い）。clone 先が同期フォルダでないかを最初に確かめること。

就活面接（両者共通）#

多視点復元は無地の面で点群が欠落し、シルエット法は凹形状を復元できないという相補的な弱点があります。そこで前者で推定したカメラ姿勢を後者の彫刻に流用し、さらに点群で凹部を補正する統合パイプラインを設計しました。単独手法との比較実験で、統合により表面誤差が○%改善することを確認しています。

開発手法について#

3D復元は精度が実測しないと分からないため、最初の3週間を技術検証に充て、そこで得た再投影誤差の実測値をもとに要件を定義しました。以降は設計→実装→テストの工程を切って進めています。作業を並行させるため、接続点となるファイル形式を最初のペアプログラミングで確定させ、それ以外はモジュール境界と作業ジャンルの境界を一致させることで、コンフリクトが構造的に起きない構成にしました。

共同開発について（2026-08-16 改訂）#

担当を人に固定せず、作業を9つのジャンルに切って管理しました。 誰がどれをやるかは、その作業に着手する時点で決めます。専門が違うメンバーでも、前提知識と重さをジャンルごとに明示しておけば、手が空いた人が取れるためです。全部を全員で書くと工数が足りないので、共同作業の濃さを「同じ画面で書く」「ジャンルを分けて書く」「レビューのみ」の3段階に分け、事故が起きると全工程に波及する座標系の規約と、ジャンル間の接続点だけを最も濃い形（ペアプログラミング）で作りました。 レビューでは「このPRが何をしているか」を自分の言葉で書くことを規約にし、形式的な承認を防いでいます。

技術的な芯について#

バンドル調整の縮小系をCG法で解く部分を自作し、前処理による反復回数の変化と、視差角が小さいときの条件数悪化を測定しました。Levenberg–Marquardt の減衰項はTikhonov正則化と形式的に同一なので、λ の選び方が収束性と精度に与える影響も実験項目に含めています。ボクセル空間から Marching Cubes でメッシュを起こしたあとの平滑化では、離散ラプラシアンの重み（一様 vs cotan）で形状の歪み方がどう変わるかを、真値メッシュとの Hausdorff 距離で定量比較しました。評価用データセットは Blender で自作し、カメラ行列と真値形状を既知としたうえで、どこで誤差が入ったかを切り分けられるようにしています。
