cameras.json 仕様#

G2（Blenderでのデータ生成）と G1（数理コア）の唯一の受け渡し口。 仕様の出どころは 計画書 §5、決定の理由は D-12・D-17。

views ブロック（1視点ぶん）#

配列で、要素1つが1視点に対応する。値は視点ごとに変わるので期待値は持たない。

フィールド型必須か意味
imagestring必須RGB画像への相対パス（基準は下記）
maskstring必須対象物体のセグメンテーションマスク画像への相対パス（基準は image と同じ）。背景と前景を分離するために使う
Rfloat[3][3]必須3×3 回転行列（world→camera）。単位行列ならワールド座標軸とカメラ座標軸の向きが一致している。読み込み時に RᵀR ≈ I と det(R) ≈ +1 を検証する（→ 検証項目 3・4）
tfloat[3]必須並進ベクトル（world→camera）。X_cam = R · X_world + t。カメラ中心のワールド座標は C_world = −Rᵀ t で求まる
sourcestring必須"turntable_gt" / "dlt" / "bundle_adjusted"。この姿勢が真値か推定値かを示す（→ 別節）
turntable_angle_degfloat必須ターンテーブルの回転角度。0.0 は初期フレーム。撮影時の事実なので、source が何であっても同じ角度が入る
reprojection_error_px`float \null`必須(null可)再投影誤差（ピクセル単位）。復元した3D点を投影し直したときのズレ。null は「まだ測っていない」の意味（下記）

パスの基準：cameras.json 自身が置かれているディレクトリからの相対とする。

source の3つの値#

その視点のカメラ姿勢が、どこから来たのかを示す。 真値と推定値の切り替えがこの1フィールドで済み、下流のコードを変更せずに実験条件を切り替えられる（→ D-12 判断③）。

値姿勢の出どころ使う場面
"turntable_gt"Blender が書き出した真値設定した値なので推定値ではない合成データ。姿勢推定を挟まずに下流だけを検証したいとき
"dlt"自作 DLT による推定値（SVD の同次最小二乗、geometry/dlt.py）姿勢推定を通したときに使用し、真値と比べて精度を測る
"bundle_adjusted"バンドル調整後の推定値（geometry/bundle.py）。姿勢と3D点を同時に微調整して再投影誤差を最小化したもの実験 E3で使用

これが撤退ラインの切り替えコストをゼロにしている。 バンドル調整が収束しなくても、source を "turntable_gt" に固定するだけで L2（既知カメラ姿勢での Visual Hull）に落とせる（→ 計画書 §12・D-25）。データ形式は同じままなので、コード変更が要らない。

1つのファイルの中で source が混在してはならない。全 views で同じ値であること（→ 検証項目 5）。 source は実験条件そのものなので、混ざったファイルは「どの条件で得た結果か」が言えなくなる。 事故として起きる形：バンドル調整が20視点中15視点だけ収束し、書き戻しでその15件だけ "bundle_adjusted" に更新される。ファイルは正常に読めてパイプラインも通り、結果だけが静かにおかしくなる。

検証項目#

load_cameras() は読み込み時に次の5つを検証し、1つでも外れたら例外を投げる（→ 計画書 §5-3）。

#検証すること検出できる事故テストでの壊し方
1schema_version が既知の版か仕様変更の取り違え??
2convention の5フィールドが期待値と一致するか規約違いのデータの混入??
3RᵀR ≈ I（各 views の R）回転行列の破損??
4det(R) ≈ +1（各 views の R）座標変換の符号ミス。−1 なら鏡映になっている??
5全 views の source が同一か実験条件の混在。書き戻しの取りこぼし??

4 が本命。 det(R) = −1 は「回転」ではなく「回転＋鏡映」で、これが通ると復元結果が左右反転したまま最後まで気づけない。

≈ の許容誤差：np.allclose(..., atol=1e-6) とする。float64 で読み書きするので、正しい回転行列なら差は 1e-12 程度に収まる。1e-6 は「丸め誤差は通すが、意味のある破損は落とす」幅として置いた。当日この値でよいか確認すること。

「テストでの壊し方」は T01 ステップ4 で埋める。1か所だけ壊した JSON を作り、pytest.raises で例外が出ることを確認する。 どう壊すかを考えることが、そのまま「何を守っているか」の理解になるので、ここは空けてある。

実装の方針：追加依存を入れない#

pydantic 等の追加依存は入れない。dataclass と json だけで書く（→ D-17・計画書 §5-3）。

検証も手書きする。上の5項目を load_cameras() の中で自分で確かめて、外れたら例外を投げる。

理由：cameras.json の書き出しは Blender 側からも io/cameras.py を再利用して行う。 Blender 用スクリプトは bpy と numpy にしか依存できないため、io/cameras.py 自身も追加依存を持てない。 ここで pydantic を入れると、G2（Blender）が io/cameras.py を呼べなくなり、書き出しと読み込みで実装が二重化する。
