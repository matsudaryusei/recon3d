3D復元プロジェクト — 決定記録#

📖 これは辞書です。頭から読まないでください。 「なんでこう決めたんだっけ？」と思ったときだけ、その番号（D-xx）を引いてください。 入口は README.md です。

作成: 2026-08-15 位置づけ: 計画書（plan.md）から「なぜそう決めたか」を分離したもの。

この文書の使い方#

計画書には決定した内容だけを書く。その根拠・検討した代替案・却下理由は全てこちらに置く。

知りたいこと見る場所
何が決まっているか（仕様・手順・日程）計画書
なぜそう決まったか（根拠・代替案・却下理由）本書
どういう経緯でテーマが選ばれたかinternal/project-handoff.md（引き継ぎ資料）

計画書の各節には → 根拠: D-07 の形で参照が入っている。その番号を本書で引く。

決定を覆したいとき#

本書の該当項目の「根拠」と「却下した代替案」に反論すること。 根拠を読まずに再提案しない。既に検討して却下した案を蒸し返すのが、この種のプロジェクトで最も時間を浪費する行動なので、それを防ぐために本書がある。

決定を変えたとき#

項目を消さずに、改訂履歴として追記する。 「かつてこう決めていて、こういう理由で変えた」が残っていること自体が、共同開発の説明材料になる。

D-01. Blender合成データで着工する#

決定: 実物撮影ではなく、Blenderでレンダリングした画像から着工する。実物は Phase 0 最終週（W03）に1セットだけ通し、本格導入は Phase 3（11月）から。

日付: 2026-08-14 ／ 計画書: §2

根拠#

① 正解が全部手に入る。 実物を撮影しても、そのマグカップの「正しい3D形状」は誰も知らない。だから復元結果が正しいかを数値で言えない。Blenderなら元の3Dモデルがそのまま真値になり、カメラ位置もシルエットも全て正解が分かる。

これは評価実験の成立条件そのもの。真値メッシュが無いと Hausdorff 距離が測れず、Phase 1 の数値目標「Hausdorff距離 ○mm以下」が立てられない。

② デバッグが劇的に楽になる。 誤差ゼロの完璧な入力を入れて答えが合わなければ、原因は100%プログラムのバグ。実物だと「バグなのか撮影が悪いのか」が切り分けられず、Phase 2 が泥沼化する。

③ 今日から始められる。 回転台・背景布・照明の調達を待たない。「8月中着工」と直接噛み合う。さらに松田の初仕事が1週目に発生する（引き継ぎ資料 §5 が心配していた「松田が6週間何もできない」問題が解決する）。モック cameras.json を手書きするより自然な形で、しかもBlenderからカメラ行列を書き出せばモックが自動生成される。

却下した代替案#

案却下理由
実写データのみで進める形状の真値が存在せず、Hausdorff距離での評価が不可能になる
実写と合成を最初から並行二系統のデータローダとテストの維持コストが工数を圧迫する

既知のリスクと対策#

合成画像は綺麗すぎる。 ノイズも影のムラもなく特徴点が理想的に取れるため、実写に移った瞬間に精度が落ちる。

→ W03 に実写を1セットだけ通す。 精度は問わず、「自分たちの被写体で特徴点が何点取れるか」という実測値だけを取る。

補足：引き継ぎ資料の誤りを1つ訂正している#

引き継ぎ資料 §6 の「ターンテーブルの回転角が真値になる」は、カメラ姿勢の真値であって形状の真値ではない。 この取り違えが、実写のみで評価実験が組めると誤認した原因だった。

D-02. 被写体に凹み形状を必須とする#

決定: 合成データ・実写データとも、必ず凹んだ形状を含む被写体を使う。主データはマグカップ相当。

日付: 2026-08-14 ／ 計画書: §2

根拠#

本プロジェクトの最重要実験は「①のみ / ④のみ / 統合」の3条件比較（E5）で、統合が優れていることを数字で証明するもの。この実験が成立するには、①が失敗する条件と④が失敗する条件の両方を含む被写体が要る。

条件失敗する手法
無地でテクスチャのない面① 多視点復元（特徴点が取れず点群に穴が空く）
凹んだ形状④ シルエット復元（原理的に削れない）

凸形状だけ（球、Suzanne など）で実験すると、シルエット法が苦手とする凹みが存在しないので、統合の意味が数字に出ない。 つまりプロジェクトの結論そのものが出せなくなる。

マグカップはこの両方を満たす（陶器の無地の面＋内側の凹み）。副データとして Stanford Bunny のような凸・高テクスチャのモデルも1つ用意し、①単独の上限性能を見る。

この決定が崩れる条件#

松田が用意する3Dモデルが凸形状だけだった場合。W01 の時点で確認する（確認シート Q18）。

D-03. 協働の型を「主担当＋副担当」にする（⚠ 2026-08-16 撤回）#

⚠ この決定は D-36 で撤回された。 現在は担当を人に固定せず、作業ジャンル G1〜G9 で管理する。 以下は撤回前の記録。 工数の考え方（315h・デバッグ時間の扱い）は現在も有効。

決定: 全てのコードに主担当と副担当を置く。詳しいほうが主担当として設計を握る。

日付: 2026-08-14 ／ 計画書: §3-2

根拠#

前提として、工数は既に飽和している。 実装の積み上げが315時間、1人あたり週8.75時間 × 18週。これは資料1 §1 の想定（週6〜10時間）のほぼ上限。

この制約から、「全てのコードを2人で書く」という運用は採れない。 同じコードを2人が書けば throughput は半分（630h・週17.5h）になり、確実に破綻する。

だから「共有するかしないか」ではなく「どこを、どの濃さで共有するか」を設計する。

副次的な利点: 「相互レビューで互いの専門を理解した」を、PR履歴という証拠付きで就活で語れる。

補足：デバッグ時間が見積もりに入っていない#

315時間の内訳にデバッグ時間は含まれていない。数値計算のデバッグは実装の1〜2倍かかるのが普通であり、実質は450〜500h規模になりうる。超過分は資料1 §1 が許容する「余裕があれば5〜6か月」（〜2027年2月）で吸収し、それでも足りなければ D-25 の撤退ラインで判定する。

D-04. 副担当も一部を実装する【2026-08-15 改訂 / ⚠ 2026-08-16 撤回】#

⚠ D-36 で撤回。 「副担当の実装比率は全体平均3割まで」という計器も廃止した（担当を人に固定しないため、測る対象が無くなった）。 代わりに progress.md はジャンル別の実働時間を記録する。 以下は撤回前の記録。 「事前の制約ではなく事後の計器にする」という考え方自体は、ジャンル制でも踏襲している。

決定: 副担当は「レビューのみ」ではなく、主担当が切り出した部分を実装する。 主担当と副担当の違いは「書くか読むか」ではなく「設計を決めるか、決まった設計の中で書くか」。

日付: 2026-08-15（D-03 の改訂） ／ 計画書: §3-2・§3-6

改訂の経緯#

初版では副担当を「PRをレビューする。実装はしない」と定義していた。これは実態と合わないため改めた。

実際に想定している協働の形は「詳しい人が主軸となって一緒に作る」であって、片方が完全に手を動かさない形ではない。初版の書き方は、工数の制約（D-03）を優先するあまり、実際にやりたいことを取り違えていた。

根拠：工数との両立#

運用総工数1人あたり週可否
全部を2人で共同実装630h17.5h✕ 破綻する
全部を1人で書き、相手はレビューのみ（初版）約350h9.7h○ だが知識が実装に定着しない
主担当が中核＋副担当が一部を実装（改訂後）約350h約9.7h◎ 採用

見積もりの根拠: 各モジュールの 1〜2割を副担当が実装し、専門外ゆえに主担当の 1.5〜2倍の時間が掛かると置くと、

0.85 + 0.15 × 1.7 ≒ 1.1  →  総工数は約1割増
315h → 約350h、週8.75h → 週9.7h

資料1 §1 の想定（週6〜10時間）には収まるが、余裕は削られている。

歯止め【2026-08-15 修正：モジュール単位 → 全体平均】#

副担当の実装比率が3割を超えると週10時間を突破して破綻する。 この数字は上の計算から出ている。

ただし「各モジュールで3割まで」という当初の書き方は誤りだった。 比重は内容によって大きく変わるため。

状況実際の比重
可視化が主体の週（バンドル調整のヤコビアン可視化など）副担当が半分近く書くことがある
専門的すぎて手が出せない週（Schur補元の導出と実装）副担当はレビューのみ＝0割

モジュールごとに3割で縛ると、この自然な変動を潰してしまう。 歯止めとして必要なのは総量の管理だけなので、次のように改める。

制約は「全体平均で3割まで」。週ごと・モジュールごとの変動は許容する。

判定は累積で行う。実績は progress.md に週次で記録し、累積の平均が3割を超えそうなら次週で調整する。それでも戻らない場合はスコープを削る（D-25 の撤退ライン）。

この修正で工数の結論は変わらない。 平均が3割に収まっていれば、上の 0.85 + 0.15×1.7 ≒ 1.1 の試算はそのまま成立する（試算は元々「各モジュールの1〜2割」という平均値で置いていたため）。

【2026-08-15 再修正】3割は「事前の制約」ではなく「事後の計器」#

関口の認識: 分担は実際にやってみないと分からない。平日はほぼ毎日会えるため、その場の会話で分担が決まることが多くなる。

これを受けて、3割の位置づけを変える。

誤った運用正しい運用
何のための数字か事前に守る上限。 超えないように作業を割り振る事後に気づくための計器。 記録して振り返り、大きく超えていたら手を打つ
超えたときにすること副担当の作業を減らすスコープか期間を見直す（D-25）

なぜ事前の制約にしてはいけないか。

3割という数字は、工数が破綻しないための条件であって、良い分担の条件ではない。 これを事前の制約として運用すると、「本当はここを一緒にやったほうがいいのに、比率が超えるから止める」という判断が起きる。それは目的と手段が逆転している。

そもそも着工前に正しい比率は分からない。 互いの得意・不得意の実像も、各モジュールの実際の難しさも、やってみるまで確定しない。事前に決めた数字を守ること自体には価値がない。

したがって：

上限は設けない。記録して、累積平均が3割を大きく超えていたら、そのとき初めてスコープか期間を見直す。

工数の試算（≒1.1）は予測であって目標ではない。予測が外れたら、予測のほうを更新する。

副次的な利点#

Approveコメント規約（D-09）が書きやすくなる。 自分が触った部分が必ずPRの中にあるため、「このPRが何をしているか」を自分の言葉で書く際の足がかりになる。

D-05. 副担当の実装範囲は「自分の専門が顔を出す部分」から切り出す（⚠ 2026-08-16 撤回）#

⚠ D-36 で撤回。 ただし「自分の得意が顔を出すところから取る」という発想は、ジャンルの選び方としてそのまま生きている（§3-2 の「やりたい人が取る」）。 以下は撤回前の記録。

決定: 副担当が実装する部分は、副担当自身の専門が活きる箇所を選ぶ。具体的な割り当ては計画書 §3-6 の担当表に持つ。

日付: 2026-08-15 ／ 計画書: §3-6

根拠#

適当に切り出すと雑用の押し付けになる。原則を置くことで3つ同時に満たせる。

  1. 副担当が短時間で戦力になる（学習コストが低い）
  2. そのモジュールの理解が、実装を通じて入る
  3. 成果物として「自分がやった」と言える（D-07 の趣旨と一致する）

なぜ可視化系が松田に寄っているのか#

意図的にそうしている。 関口のモジュール（DLT・三角測量・バンドル調整・CG法）は「数字は出るが目に見えない」ものばかりで、絵が付かないとデバッグも成果発表も成立しない。

つまり可視化は雑用ではなく、デバッグと成果発表の生命線。そこに松田の専門が最短で効く。

具体例：

  • 再投影の可視化 → 再投影誤差が「見える」ようになるのでデバッグの主力になる
  • ヤコビアンの疎パターンの可視化 → 「疎とはどういう形か」が図で分かる。説明素材としても効く
  • 残差の収束グラフ → E4実験の図がそのまま作れる

D-11. 座標変換を1ファイルに閉じ込め、機械的に検査する#

規約を決めることより、規約を破れない構造を作ることが本質。

D-12. cameras.json のスキーマ設計（4つの判断）#

決定: スキーマは計画書 §5-1 のとおり。convention ブロック、extrinsic_form、source、mask パスを持つ。

日付: 2026-08-14 ／ 計画書: §5

判断① convention ブロックをファイル自身に埋め込む#

規約はドキュメントにも書くが、データファイル自身にも書く。 半年後に data/ から出てきたJSONが、どの規約で書かれたか単体で分かる状態にするため。読み込み時に検証し、想定と違えば例外を投げる。

判断② extrinsic_form を明示する#

X_cam = R·X_world + t（world→camera）なのか、その逆なのかを文字列で持つ。

ここが曖昧だと R と Rᵀ の取り違えが起き、しかもそれらしい結果が出てしまうため発見が遅れる。3D復元で最も頻度の高い事故。

判断③ source フィールドが実験設計の骨格になる#

取りうる値："turntable_gt" / "dlt" / "bundle_adjusted"

引き継ぎ資料 §5 の「回転台の真値 vs ①の推定値」の切り替えが、この1フィールドだけで表現できる。 同じ形式のまま中身を差し替えれば、下流のコードを一切変更せずに条件を切り替えられる。

これが撤退ライン L2 への切り替えコストをゼロにしている（D-25）。バンドル調整が収束しなくても、source を turntable_gt に固定すればコード変更なしでVisual Hullに全リソースを振れる。

判断④ mask のパスを同じファイルに入れる#

引き継ぎ資料 §5 の「④が待っているのは cameras.json という1ファイルだけ」を文字通り実現する。ボクセル彫刻は cameras.json を読めば、画像もマスクもカメラ行列も全部たどれる。

補足：pydantic を使わない理由#

dataclass ベースで実装する。D-17（Blender用スクリプトは bpy + numpy のみ）の制約のため。 cameras.json の書き出しに io/cameras.py を再利用したいが、そのためには io/cameras.py 自体も追加依存を持てない。

D-19. 合成データのレンダラを EEVEE にする#

決定: tools/blender_render.py の既定レンダラは EEVEE。Cycles はレンダリング品質の影響を見る追加実験でのみ使う。

日付: 2026-08-15 ／ 計画書: §7-6

根拠#

松田の環境では Cycles が CPU レンダリングになる。

blender_system/system-info.txt の Cycles 欄に挙がっているのは CPU device capabilities: AVX2 の1行のみで、GPU計算デバイス（Intel oneAPI 等）が列挙されていない。 GPUは内蔵の Intel Iris Xe。

20方向 × 複数データセット × 反復試行のレンダリングを CPU Cycles で回すと、現実的な時間に収まらない。

そして要件から見て EEVEE で足りる。 本プロジェクトが合成データに求めるのは「カメラ行列・シルエット・真値メッシュと整合した、一貫性のある画像」であって、物理的に正確な大域照明ではない（D-01）。特徴点検出とセグメンテーションが成立すれば要件を満たす。

未確認事項 → ✅ 解消（2026-08-16）#

Preferences → System → Cycles Render Devices に oneAPI が出るかを一度確認する（松田の回答・2026-08-16）→ タブ（CUDA / OptiX / HIP / oneAPI）は並ぶが、選択できるデバイスは0件という回答だった。Cycles の GPU レンダリングは使えない。推定が実機で裏づけられ、EEVEE 既定の根拠が確定した。

派生する影響#

L4 のリアルタイムビューア（D-08）の実現性も、内蔵GPU前提で控えめに見積もる。 解像度を落とすか、更新頻度を落とす前提で考える。

D-20. マスク出力時は View Transform を Standard にする#

決定: マスク（シルエット）画像を出力する際、カラーマネジメントの View Transform を Standard に設定する。スクリプト内から明示的に設定し、UI設定に依存させない。

日付: 2026-08-15 ／ 計画書: §7-6

根拠#

Blenderの既定のビュー変換は AgX（4.0 以降）で、トーンマッピングを掛けるため画素値がそのまま出ない。

シルエット／マスクは「白＝物体・黒＝背景」の二値が正しく出ることが要件なので、ここでトーンマッピングが挟まると閾値処理が壊れる。

スクリプトから設定する理由: 人が設定を戻し忘れる事故を防ぐため。D-11 と同じ思想（規約を破れない構造を作る）。

関連する方針#

マスクはカラー画像を後から閾値処理して作るのではなく、Blender側で直接出力する（アルファまたは Holdout / Cryptomatte 等）。手法は松田に委ねるが、「マスクの生成方法」を docs/notes/ に1本残すこと。

2026-08-16 改訂: 松田から「Blenderでマスク処理をしたことがないため判断不可」という回答があったため、「手法は松田に委ねる」を撤回する。 関口が候補を提示し、W02 に2人で決める（→ D-35）。docs/notes/ に1本残す方針は維持する（書き手は実装した側）。

D-21. ボクセル投影をチャンク分割で実装する#

決定: geometry/carving.py は、ボクセルをチャンクに分割して投影する。全ボクセルを一度に 4×N へ展開しない。チャンクサイズは外部パラメータにする。

日付: 2026-08-15 ／ 計画書: §7-6

根拠#

256³ = 1677万ボクセル。占有グリッド自体は小さいが、計画書 §7-5 の「行列で一括投影する」方式は中間バッファが大きい。

配列256³128³
占有グリッド（uint8）17 MB2 MB
全ボクセル中心の同次座標 4×N（float64）537 MB67 MB
投影結果 3×N（float64・カメラ1台分）403 MB50 MB

素直に書くと 256³ で一時的に 1 GB 前後を要求する。松田のGPUは内蔵（Iris Xe）でシステムメモリを共有するため、実効メモリはさらに目減りする。

メモリ 8 GB だと厳しく、16 GB なら通るという線。松田のメモリ容量が未回答 → 2026-08-16 に 16 GB と判明（D-32）。256³ を既定として維持する。

それでもチャンク分割は撤回しない。 16 GB は「OS・ブラウザ・Blender・内蔵GPUの共有分を差し引いた実効値」で見ると余裕のある数字ではなく、素直に書けば 1 GB 前後の一時確保が残るため。どちらに転んでも動く実装にしておく方針は維持する。

「ループではなく行列演算」方針との関係#

§7-5 の方針は維持する。 チャンク内では行列演算で書く。チャンク分割はメモリ制約への対応であって、ループ実装への後退ではない。

副次的な利点#

E7（実装方式の速度比較）の独立変数にチャンクサイズを追加できる。 キャッシュ効率との兼ね合いで最適値が出るはずで、実験項目として素直に成立する。

根拠#

副担当の比重は、モジュールの内容によって必然的に変わる。

状況副担当の比重
可視化が主体（ヤコビアンの疎パターン、収束グラフ）高くなる。半分近く書くこともある
専門性が高く手が出せない（Schur補元の導出と実装）ゼロ。レビューのみ
独立したテストを切り出せる（メッシュの整合性検証）中程度

着工前に机上で引いた表が、この変動を正しく予測できるはずがない。 表を固定して運用すると、次のどちらかが起きる。

  1. 表に合わせて不自然な分担をする（手段が目的化する）
  2. 表を無視して進み、計画書が実態を映さなくなる

どちらも避けたいので、表を動かす前提にして、動かした事実を記録する運用にした。

なぜ「記録」までするのか#

比重を可変にするだけなら記録は要らない。それでも残すのは3つの理由から。

  1. 歯止めの判定に要る。 D-04 の「全体平均で3割まで」は、累積で見ないと判定できない。 週単位の実感では分からない。
  2. 計画書の更新漏れを検出できる。 記録に「初期案からの変更」欄を置き、計画書側を直したかを併記する。
  3. 就活の説明材料になる。 「相互レビューで互いの専門を理解した」を、どの機能を誰が書いたかという具体で語れる。PR履歴と対になり、証拠としての強度が上がる（D-09 と同じ発想）。

  • 週次（週1回の対面Issue切りの場・§8-3）に1行追加
  • Phase の切れ目に振り返りを書き、必要なら計画書 §3-6 を更新
  • 更新したら、進捗記録の「決定を変えた記録」と本書の改訂履歴の両方に残す

D-29. 同席作業を既定とし、ペアプロと区別する#

決定: 同じ場所で各自の作業をする「同席作業」を既定の働き方とする。 これはペアプロ（1つのコードを2人で書く）とは別物として扱う。

日付: 2026-08-15 ／ 計画書: §3-3

背景#

関口の認識：平日はほぼ毎日会える。相手が作業しているところを目にすることが多い。任せっきりにならず共同で作業するつもりでいる。

この条件は、それまでの文書が暗黙に想定していた働き方（各自が別の時間・場所で作業し、PRで同期する）とは異なる。

根拠：2つの軸を混同していた#

D-04 までの記述は「共同作業の濃さ」を1軸で捉えていた。しかし実際には独立した2軸がある。

軸選択肢throughput への影響
同席するか（いつ・どこで）同席作業 / 非同席ほぼゼロ
同じコードを書くか（何を）ペアプロ / 分担実装 / レビューのみペアプロは半分

混同すると「一緒に作業する ＝ 高コスト」という誤った結論になる。 実際には、同席していても各自が別のファイルを書いていれば throughput は落ちない。

同席作業が最も割の良い形である理由#

費用がほぼ掛からないのに、利点だけがある。

  1. 質問の敷居が下がる。 「これ聞いていいのかな」と迷う時間が消える。専門が違う2人にとってこれは大きい
  2. 相手が何をしているかが自然に分かる。 D-03 が PR レビューで実現しようとしていたことの一部が、日常的に達成される
  3. 詰まりが早く解ける。 数値計算のデバッグは「詰まって数日溶ける」形で工数を食う（D-03 補足）。その場で聞ける相手がいることの効果は、見積もりに表れない部分で大きい

したがって、ペアプロを3か所に限定していること（D-06）は「普段は別々に作業する」という意味ではない。 普段から同席し、そのうえで同じコードを2人で書くのを3か所に限る、という意味である。

これは実害が出るので明記する。

根拠#

要望は正当で、かつ志望分野と一貫している。 松田の志望研究室のテーマには「透過と映り込みの表現」が含まれており、レンダリングへの関心は思いつきではない。

しかし「レンダリング品質を上げる」方向に伸ばすと、本プロジェクトの評価軸と噛み合わない。 合成データに求めているのは物理的な正確さではなく、カメラ行列・シルエット・真値メッシュとの整合性である（D-19）。綺麗な絵を作っても、この計画では測る対象がない。

だから「レンダリングを研究する」ではなく「レンダリング条件を独立変数にする」形にする。

案採否理由
照明・シェーディング・露出・背景を振り、マスクIoU と復元精度への影響を測る（E8）本命既存の評価基盤（Hausdorff距離・IoU）をそのまま使えるため追加工数が小さい。 かつ「レンダリング設計が復元精度を左右する」という主張は、画像工学研究室の文脈でそのまま語れる
EEVEE / Cycles の品質比較副次D-19 で既に「余力があれば」の追加実験として存在。CPU レンダリングのため枚数を絞る必要がある
レンダラそのものを自作する却下18週に収まらない。D-18（自作とライブラリの線引き）の趣旨にも反する
物理ベースの材質表現を作り込む却下測る対象がない。合成データの要件から外れる

工数#

E8 を追加しても総工数は増やさない。 レンダリング条件を振るのは既存の tools/blender_render.py のパラメータ操作であり、評価は Phase 4 の実験枠（40h）の中で E1〜E7 と同じ計測基盤に乗る。 採否を W04 まで待つのは、W02 の実装で松田がどれだけ余裕を持てるかを見てから決めるため。

松田は Q-c のコメントで次のように書いている。

D-38. プロジェクトをパッケージとして扱い、editable install で import recon3d を通す#

決定: pyproject.toml に [build-system]（hatchling）と [tool.hatch.build.targets.wheel] packages = ["src/recon3d"] を置き、uv sync にプロジェクト自身を editable install させる。あわせて、骨格作りの範囲を「uv run pytest が 1 passed になるところまで」に固定する（計画書 §6-2）。

日付: 2026-08-20 ／ 計画書: §6-2・§6-3 ／ 判断者: 関口

経緯#

.gitignore・pytest・.python-version が入り、G6 の「器」で残るのはディレクトリ骨格だけになった。ところが src/recon3d/ を置いても、import recon3d が通る設定を決めていなければテストが書けない。 骨格に着手する前に、この1点を決める必要があった。

根拠#

  1. CLI エントリポイントを持つ計画だから（§6 の tools/run_pipeline.py）。対抗案だった pytest の pythonpath = ["src"] は設定1行で済むが、通るのは pytest 実行中だけで、uv run python tools/run_pipeline.py からは import recon3d が通らない。あとで必ず作り直しになる。
  2. uv sync 1回で全端末に揃うから。 editable install は uv sync が自動で行うため、3台（Windows / Ubuntu / mac）で手順が増えない。PYTHONPATH を各自の環境変数に設定させる案は、環境差の温床になるので採らない。
  3. src/ レイアウトの利点を保てるから。 インストールされたものを import するので、リポジトリのルートで実行したときだけ通るという事故が起きない。

実装上の落とし穴（確認済み）#

  • ⚠️ packages = ["src/recon3d"] の明示は必須。 [project] name が 4bitcom-HandM でパッケージ名 recon3d と一致しないため、省略すると hatchling がビルド対象を決められず uv sync が失敗する（2026-08-20 に再現を確認）。
  • uv.lock が1行変わる：source = { virtual = "." } → source = { editable = "." }。依存関係は増えないので、この差分はコミットしてよい。
  • src/recon3d/ がまだ無い状態でも uv sync は成功する（空のwheelが建つ）。つまり設定だけ先に入れてもリポジトリは壊れないが、import recon3d は骨格ができるまで通らない。
  • ⚠️ ただし、その順序でやると後から src/ を作っても uv sync が再ビルドしない（Audited で素通りし、import recon3d が失敗し続ける）。uv sync --reinstall-package 4bitcom-handm が必要（2026-08-20 に遭遇・解消）。git pull で src/ ごと受け取る端末では起きないため、この落とし穴を踏むのは設定を先に入れた1台だけ。

骨格の範囲を同時に決めた理由#

§6 のツリーは完成時の姿であり、そのまま「作るもの一覧」として読むと、着手前に空ファイルを数十個置くことになる。それは着手時に「空ファイルを消して作り直す」無駄なコンフリクトを生むだけなので、骨格は __init__.py と .gitkeep だけとし、個別モジュールは実装する人が担当週に作ると決めた（§6-2）。完了判定を uv run pytest の結果という機械的な基準に置いたので、「どこまでやれば終わりか」で揉める余地が無い。

この決定が崩れる条件#

  • 配布形態を変える場合（例：Blender アドオンとして固める）。そのときは [project.scripts] や同梱方法を含めて組み直す。
  • hatchling 以外のビルドバックエンドに移る場合。packages の書き方が変わる。

D-39. リポジトリを同期フォルダ（iCloud Drive 等）の下に置かない#

決定: 各自の作業コピーはローカルのディレクトリに置く（例：~/Projects/4bitcom）。iCloud Drive・OneDrive・Dropbox・Google Drive の同期フォルダ配下には clone しない。

日付: 2026-08-20 ／ 計画書: §7-8 ／ 判断者: 関口

経緯#

骨格が完成し uv run pytest が 1 passed になった直後、同じ端末で同じコマンドが ModuleNotFoundError: No module named 'recon3d' で落ちた。 調べた結果、コードの問題ではなく iCloud Drive が原因だった。

  1. uv は .venv に macOS の hidden フラグを付ける（これは正常な動作）
  2. iCloud Drive がそのフラグを .venv 配下の全ファイルに伝播させる（691ファイル中691件）
  3. CPython の site.py（addpackage）は、hidden が付いた .pth ファイルを読み飛ばす
  4. editable install のパスを教える _editable_impl_*.pth が無視され、src/ が sys.path に入らない → import recon3d が失敗

chflags nohidden で外すと直るが、1分ほどで iCloud が付け直すため対症療法にならない。あわせて .venv/lib 2 という衝突コピーも生成されていた。

根拠#

  1. Git と役割が完全に重複している。 同期はリポジトリの仕事であり、ファイル同期サービスが上に重なると衝突コピーという「誰も編集していない差分」が生まれるだけ。
  2. 壊れ方が分かりにくい。 今回の症状は「さっきまで通っていたテストが、何も変えていないのに落ちる」。原因がコードの外にあるため、デバッグに時間を取られる（実際に取られた）。
  3. .venv は再生成できる。 同期して守る価値がそもそも無い（.gitignore 済み）。

やったこと#

~/Library/Mobile Documents/com~apple~CloudDocs/vscode/Project/4bitcom → ~/Projects/4bitcom へ移動し、rm -rf .venv && uv sync で作り直した。.git/ ごと移動するため、remote 設定・追跡ブランチ・履歴はそのまま（git remote -v・git ls-remote origin・git status -b で確認済み）。移動後は hidden 0件、uv run pytest は 1 passed。

他の端末への注意#

  • Windows の OneDrive は同じ罠を持つ。 デスクトップ や ドキュメント が既定で OneDrive 配下になっている構成が多いので、clone する場所を最初に確認すること（例：C:\dev\4bitcom）。
  • 症状が出るのは .pth を使う仕組み全般（editable install）。D-38 の方式に固有の弱点ではなく、pythonpath 方式に逃げても別の形で衝突コピー問題は残るので、D-38 は維持する。
