手順書の作り方（新しいタスクを足すとき）#

番号を1つ進めて、T<番号>-<内容>.md で作ります。 中身は既存のどれかをコピーして、下の6ブロックを埋めてください。

ブロック中身
1. 見出しの表ジャンル / 目安時間 / 前提 / 作るもの / 仕様の出どころ（plan.md・decisions.md へのリンク）
2. なぜやるのか2〜4段落。これが無いと「言われたからやる」になり、判断が入らなくなります
3. ステップ打ち込むコマンドをそのまま載せる。 「◯◯を設定する」で止めない
4. 完了判定チェックボックス。 「動いた」ではなく「何をどう見たら分かるか」を書く
5. つまずいたら症状 → 対処の表。実際に踏んだものを足していく
6. 終わったら進捗ログへの記録・next.md の更新・次に繋がるタスク

仕様そのものはここに書きません。 計画書に書いて、ここからリンクします。 二重に書くと必ず食い違い、どちらが正か分からなくなります。 食い違ったときは計画書と決定記録が正です。

⚠️ どこまで書くか（手順書を足す人へ）#

手順書は「工夫する余地を奪わない」ことを条件に書きます。 全部書けば親切、ではありません。

全部書く書かない（空けておく）
環境構築・ツールの操作（uv・Git・GitHub の画面）アルゴリズムの導出・数式の変形
設定ファイルの中身（ci.yml・ラベル定義）実装コード（関数の形と、通すべきテストまで）
打つコマンドと、その期待出力テストの期待値（自分で導いてもらう）
完了したと分かる観測方法比較の結論・設計の選択（どちらが良いか）
詰まったときの対処（既知の罠）調べれば分かることの要約

判断の基準は1つです。

「そこで詰まって時間を使うことに、学びがあるか」

  • uv sync が通らずに2時間溶かす → 学びはない。だから全部書く
  • 座標変換の符号を自分で導いて間違える → その間違いが理解になる。だから書かない

迷ったら「書かない」側に倒し、代わりに 学びの入口 に資料を1本足してください。
